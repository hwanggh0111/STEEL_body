# STEEL BODY

운동 기록 PWA. 운동·인바디를 기록하고, 루틴·홈트·측정으로 이어간다. 미션이 이어가는 이유를 만든다.

- **Frontend** `frontend/` — React 18 + Vite + Zustand + Recharts
- **Backend** `backend/` — Node.js + Express + JSON 파일 DB, JWT 인증
- **배포** Render (`render.yaml`)

```bash
cd frontend && npm run dev     # http://localhost:5173
cd backend  && npm start       # http://localhost:4000
cd frontend && npm run check   # 화면 여럿이 같이 쓰는 계산 확인 (테스트 틀이 없어서 이걸로 본다)
```

# 개발 일지

최신이 위. 날짜 하나에 그날 한 일을 묶는다.

## 2026-08-27

**어제 것을 아홉 덩이로 나눠 묶었다.**

54개 파일이 커밋 없이 작업 트리에 그대로 있었다. 한 덩이로 묶으면 나중에
어느 것이 어디서 왔는지 못 찾는다. 화면 단위로 갈랐다 — 홈 / 관리자 /
고객센터 / 기록·인바디·측정 / 로그인·회원가입·알림 / 홈트·휴식 타이머·껍데기 /
서버 / `npm run check` / 문서·공지. 묶기 전에 `npm run check` 와 빌드를 돌렸다.

### 자주 묻는 것이 두 개였다

고객센터의 `자주 묻는 것`은 **기록 보관**과 **정지** 둘뿐이었다.
두 곳이 이 목록을 본다 — 고객센터의 「자주 묻는 것」과, 제보함에서 유형을
고르기 전에 나오는 「무엇이 궁금하세요?」다. 답이 두 개면 나머지는 전부 제보로
들어온다. **물어본 사람은 며칠을 기다리고, 답하는 쪽은 같은 답을 또 쓴다.**

열세 가지를 더 채워 열다섯이 됐다 — 알림 · 소셜 로그인 · 비밀번호 · 기기 변경 ·
내보내기 · 인바디 판정 · 1RM · 루틴 · 홈트 · 제보 답변 · 계정 삭제 · 점검 · 사진.

**감으로 쓰지 않았다.** 답을 적기 전에 앱이 실제로 뭘 하는지 하나씩 봤다 —
`backend/src/routes/` 의 엔드포인트, `RemindersPage.jsx` 가 열쇠 없을 때
켜기 단추를 아예 안 그린다는 것, 내보내기가 기록 화면(운동·인바디)과 측정
화면(측정) 두 곳에 나뉘어 있다는 것, 1RM 이 Brzycki 이고 10회까지만 받는다는 것,
제보 답이 이메일이 아니라 제보함 안에 붙는다는 것(`reports.js` 의 `reply`).

**세 가지는 「안 된다」고 적었다.**

- **운동 알림** — 열쇠가 없어 지금은 안 나간다. 켜기 단추가 안 보이는 이유까지 적었다
- **소셜 로그인** — 아직 안 붙은 곳이 있다. 이메일로 가입하면 나중에 같은
  이메일의 소셜로도 들어올 수 있다는 것을 같이 적었다
- **계정 삭제** — 화면에서 지우는 길이 없다. 찾아보니 정말 없었다(`탈퇴` 가
  프론트에도 서버에도 없다). 제보함으로 받는다고 적었다

없는 기능을 있는 것처럼 적으면 **그 자리에서 제보가 늘 뿐이다.**

### 단추 열다섯 개는 길을 막는다

제보함의 「무엇이 궁금하세요?」는 `FAQ` 를 전부 단추로 깔고 있었다. 두 개일 때는
됐는데 열다섯이 되면 **네 줄짜리 벽**이 되어, 제보하러 온 사람이 그걸 다 지나야
한다. 앞의 여섯 개만 내놓고 나머지는 이미 있던 「모두 보기」로 보냈다.

### 확인을 또 버리지 않았다

어제 만든 `npm run check` 에 자주 묻는 것을 넣었다. **항목을 늘릴 때마다 서로
걸려들기 쉬운 자리다** — 키워드가 겹치면 엉뚱한 답이 위로 온다. `푸시 → 알림`,
`탈퇴 → 계정 삭제`, `등급 → 인바디 판정` 처럼 열 가지 말이 제 답으로 가는 것,
`topic` 이 안 겹치는 것, 한 글자로는 안 찾는 것을 본다.

**개수는 못박지 않았다.** `항목 수 === 15` 로 두면 항목을 하나 늘릴 때마다 여기부터
고쳐야 한다. 줄어든 것만 잡는다.

### 남은 것

- **Render 배포** — 내가 여는 길이 없다
- VAPID · 소셜 · SMTP 열쇠 — `render.yaml` 에 자리만 있다

## 2026-08-26

**남은 두 화면을 다시 만들었다 — 홈과 관리자.**

### 홈 — 매일 여는 화면이 오늘 뭘 할지를 안 말했다

420줄짜리 한 파일에 로고 · 검색 · 오늘의 요약 · 통계 셋 · 미션 · 주간 달력 ·
주간 요약 · 빠른 이동 여덟 덩어리가 순서 없이 쌓여 있었다. 읽어보니 **문제는
덩어리가 많은 것이 아니라 그중 어느 것도 「지금 뭘 할 차례인가」를 말하지 않는
것**이었다.

**1. 홈이 하던 일을 몰랐다.** 어제 붙인 루틴 진행표는 기록 화면에만 있다.
그래서 루틴을 시작해두고 홈으로 오면 홈은 「아직 오늘 운동 기록이 없어요」라고 했다.
**시작해둔 사람에게 시작하라고 말하고 있었다.** 홈도 `/routine-session` 을 보게 했다.

그 김에 「오늘」 자리를 카드 하나로 합치고, 순서를 우선순위로 삼았다 —
하던 루틴 → 오늘 기록 → 만들어둔 루틴 → 아무것도 없음. **한 번에 한 가지만 말한다.**
세 번째 갈래에서는 홈에서 곧바로 루틴을 시작한다. 루틴 화면이 시작할 때 묻는
「하던 걸 바꿀까요」는 여기서 안 묻는다 — 하던 것이 있으면 첫 번째 갈래로 빠지므로
그 상황 자체가 안 온다.

**2. 같은 주를 세 번 그리고 있었다.** 통계 상자의 「이번 주 n/7」, 주간 달력,
주간 요약의 「운동한 날」이 전부 같은 수였다. `WeeklyReport` 에는 「달력이 어느 날
했는지를 보여주니 여기서는 얼마나 했는지만 말한다 — 같은 주를 두 번 그리지 않는다」고
주석까지 적어놨는데, **그 위의 통계 상자가 세 번째였다.** 상자 줄을 걷어냈다.
평생 누적 「총 운동」은 36px 숫자를 차지할 말이 아니라 달력 아래 한 줄로 내렸다.

**3. 「빠른 이동」 일곱 칸이 전부 아래 탭바의 복사본이었다.** 기록 · 인바디 · 루틴은
탭바에 늘 떠 있고, 홈트 · 측정 · 히스토리 · 고객센터는 더보기 안에 있다. 새로 가는
곳이 하나도 없었다. **한 번에 닿는 것을 홈에서 또 그릴 이유가 없다** — 두 번 눌러야
하는 더보기 쪽만 남기고, 거기 빠져 있던 운동 알림을 넣었다. 일곱이 여섯이 됐다.

**검색에서 두 항목이 아무 데도 안 갔다.** 「미션」과 「이번 주 운동」이 `path: '/home'`
만 들고 있었다. 홈에서 누르면 홈으로 가라는 뜻이라 정말 아무 일도 안 일어났다.
코드에는 `scroll` 처리가 이미 있었는데 **그걸 쓰는 항목이 하나도 없었다.** 세 자리에
`id` 를 붙이고 셋 다 그 자리로 데려가게 했다. 검색창 예시에 아직 「이벤트」라고 적혀
있던 것도 고쳤다 — 이벤트 페이지는 어제 지웠다.

**나머지.**

- 검색 250줄을 `components/home/HomeSearch.jsx` 로 뺐다. 홈 파일의 절반이 초성
  매칭과 최근 검색 목록이었다. 데려가는 길도 하나로 모았다 — 목록 · 최근 검색 ·
  Enter 가 각자 같은 코드를 세 번 적고 있었다
- 주간 달력에서 **운동한 날을 누르면 그날 히스토리**로 간다. 히스토리가 `state.date`
  를 받게 했다 — 달력만 보여주고 아무 데도 안 데려가는 칸이었다
- 최근 체중은 통계 상자에서 한 줄로 내려왔다. **2주 넘게 안 적었으면 짚어준다.**
  기록이 없으면 `-` 를 36px 로 띄우던 것을 아예 안 그리게 했다 — 없는 것을 크게
  띄우는 자리는 없앤다
- 로고가 첫 화면의 3분의 1을 먹고 있었다 (56px 아이콘 + 42px 글자). 매일 오는 사람은
  앱 이름을 이미 안다. 한 줄로 줄여 날짜를 옆에 붙였다
- 불러오는 동안 화면 전체가 「로딩 중...」 한 덩어리로 바뀌던 것을 카드 한 줄로 줄였다

### 관리자 — 어디에 손볼 것이 남았는지 일곱 개를 다 눌러봐야 알았다

탭 일곱 개가 한 줄로 늘어서서 줄바꿈됐다. 「보안 관리」 · 「해킹 보안」 ·
「AI 관리자」 · 「보안 검사」 — **이름만 보고는 어느 것이 무엇을 하는지 알 수 없다.**

더 이상한 것은 이것이다. 아래 탭바의 「관리자」에는 8/24에 손볼 제보 수를 뱃지로
붙여뒀는데, **정작 관리자 화면 안에는 그 숫자가 없었다.** 여기까지 들어온 사람이
제일 먼저 알아야 할 숫자다.

- **할 일을 맨 위에 적는다.** 답을 기다리는 제보와 확인 안 한 욕설 신고를 센다.
  없으면 없다고 말한다 — 빈 목록을 보고 짐작하게 두지 않는다. 그래서
  `usePendingReports` 가 `loaded` 를 같이 돌려준다. **아직 안 받아온 0 과 정말 0 은
  다르다** — 안 받아온 0 으로 「손볼 것이 없어요」를 띄우면 그건 거짓말이다
- **두 무리로 나눴다.** 사람이 기다리는 것(제보 · 못 찾은 말 · 점검)과 지켜보는
  것(보안 넷). 앞의 셋은 안 보면 사람이 기다리고, 뒤의 넷은 아무 일 없으면 안 열어도
  된다. 성격이 다른 것을 한 줄에 섞어놨었다
- **항목마다 무엇을 하는 곳인지 한 줄씩** 붙였다. 측정 시스템을 다시 만들 때와 같다
- 열리는 탭은 그대로 제보다. **매일 하는 일을 한 번도 안 눌러서 닿게 두는 것**이
  8/24에 정한 것이라 그건 안 바꿨다 — 나머지는 「관리 항목」을 눌러 고른다
- `nickname` 을 꺼내놓고 어디에도 안 쓰고 있었다. 관리자 계정이 둘 이상일 수 있으니
  지금 누구로 보고 있는지를 머리에 적는다

### 나머지 화면도 전부 다시 만들었다

홈과 관리자를 끝내고 「고객센터는 최신이라 그대로 두겠다」고 **먼저 말했다.** 어제
같은 것으로 지적받은 자리다 — 안 한다고 먼저 말하지 않기로 했는데 또 그랬다.
읽어보니 고객센터도 걸리는 것이 있었다. 남은 화면을 하나씩 다시 만들었다.

**고객센터 — 이름이 「고객센터」인데 볼일 앞에 소개가 서 있었다.**
들어오면 감성 문구 두 덩어리, 만족도 별점, 「지금까지 몇 회 적었다」, 「무엇을 할 수
있나」 여섯 줄을 지나야 제보함이 나왔고 **그마저 접혀 있었다.** 여기 오는 이유는
셋뿐이다 — 안 되는 것을 말하러, 답을 찾으러, 뭐가 바뀌었나 보러.

- **갈래를 밖에서 고른다.** 「안 되는 게 있어요 / 어떻게 쓰는지 모르겠어요 /
  이랬으면 좋겠어요」 셋을 앞에 놓고, 누르면 제보함이 그 유형으로 열린다.
  예전에는 「제보함 열기」를 누른 뒤 안에서 버그·문의·건의를 또 골랐다.
  **말도 「버그」가 아니라 사람이 하는 말로 적었다** — 자기가 겪은 일이 「버그」인지
  「문의」인지 먼저 판단하게 하면 거기서 막힌다
- **답이 왔는지가 맨 위로** 왔다. 예전에는 페이지 맨 아래 접힌 단추 안에만 있었다
- 만족도는 아래로 내렸다. **안 되는 것을 말하러 온 사람 앞을 막고 별점을 묻고 있었다**
- 소개(히어로 문장 · 내 이야기 숫자 · 기능 목록)는 **지우지 않고 「이 앱은」으로 접었다.**
  처음 온 사람은 펼쳐 읽고, 매일 오는 사람은 안 본다
- 앱 정보에 **「기록은 서버에, 게임 진행은 이 기기에」**라고 적혀 있었다. 게임은
  어제 전부 걷어냈다 — 없는 기능을 앱 정보가 말하고 있었다
- 제보의 「어느 화면」 목록에 **운동 검색과 운동 알림이 빠져 있었다.** 없는 화면의
  버그는 「그 밖에」로 오는데, 그러면 어느 화면인지 물어본 뜻이 없어진다.
  「무엇을 할 수 있나」 목록에서도 이 둘이 빠져 있었다

**기록 — 날짜 칸이 폼 맨 아래에 있었고, 그게 목록의 날짜를 겸했다.**
어제 것을 적으려면 운동 · 무게 · 세트 · 횟수를 다 적고 나서야 날짜를 만났다.
그리고 그 값을 바꾸는 순간 **아래 오늘 목록이 통째로 사라졌다** — 무슨 일이
일어난 건지 알 수가 없다. 날짜를 폼 맨 위로 올리고 「오늘 · 어제 · 다른 날」로
고르게 했다. 오늘이 아니면 그렇다고 적고 「오늘로」를 준다.

- 그 날 한 것을 폼 위에 한 줄로 (개수 · 세트 · 볼륨). 목록까지 내려가지 않아도 안다
- 「다른 운동」이라는 단추가 입력칸 아래에 따로 있었다. 하는 일은 칸을 비우는 것뿐인데
  이름만으로는 알 수 없다 — **지우는 자리는 칸 안이 제자리다**
- 빈 상태의 「+ 운동 기록하기」가 `document.querySelector('form input')` 으로 첫 칸을
  찾고 있었다. 폼 맨 위에 날짜 칸이 생기면 엉뚱한 데 초점이 간다 — ref 로 짚는다
- 화면에 한국어가 하드코딩된 자리 다섯을 `TEXT` 로 옮겼다. 영어로 바꿔도 한국어가
  남던 곳들이다

**인바디 — 입력 폼부터 열리고, 그래프가 맨 아래에 있었다.**
인바디는 2주에 한 번 적고 그 사이에는 보러 온다. 보러 온 사람 앞에 빈 칸부터
들이밀고, 정작 보러 온 **체중 그래프는 기록 목록보다도 뒤**에 뒀었다.

- 맨 위는 「지금」이다 — 지금 몇 kg, 지난 기록보다 어느 쪽으로, 며칠 전
- 폼은 접었다. 기록이 하나도 없으면 처음부터 펼친다. 홈의 「기록하러 가기」로
  들어오면 폼까지 열어준다 — 눌렀는데 또 단추를 찾게 두지 않는다
- **BMI 를 「과체중」 · 「비만」 · 「고도비만」이라고 부르고 있었다.** 어제 「신체 분석」을
  다시 만들면서 **몸에 등급을 매기지 않기로** 했는데, 같은 화면 안에서 아래쪽은
  「일반적인 범위」라고 하고 위쪽 폼은 「비만」이라고 하는 상태였다. 눈금을
  `data/bodyRanges.js` 한 군데서 가져와 말을 맞췄다
- 「간편 / 상세」가 무엇이 다른지 눌러봐야 알았다. 한 줄씩 적었다
- 지난 기록을 전 기간 다 쏟아내던 것을 최근 5건 + 「더 보기」로 바꿨다

**로그인 — 늘 쓰던 사람이 매번 소셜 버튼 넷을 지나 내려가야 했다.**
「돌아오셨군요! 근호」라는 인사조차 그 아래에 파묻혀 있었다. 전에 들어온 적이 있으면
**쓰던 길을 위로** 올린다. 처음 온 사람에게는 소셜이 위다 — 가입까지 한 번에
끝나기 때문이다. 없앤 것은 없고 순서만 바꿨다.

- 자동 로그인 체크박스에 「다음부터 이 기기에서는 바로 들어옵니다. 공용 기기에서는
  꺼주세요」를 붙였다. 이름만으로는 켜도 되는 자리인지 알 수 없다
- 로그인 단추가 왜 안 눌리는지 적는다. 죽어 있는 단추만 보고 짐작하게 두지 않는다

**회원가입 — 이메일은 알아서 확인하는데 아이디만 단추를 눌러야 했다.**
안 누르면 가입 단추가 영영 안 눌렸고, 그것 하나 때문에 「아이디 옆 중복확인을
눌러주세요」라는 안내를 따로 적어둬야 했다. **안내로 메울 것이 아니라 이메일과 같게
만든다** — 이제 치면 알아서 확인한다. 단추가 없어졌다.

**운동 알림 — 켤 수는 있고 끌 수는 없었다.**
서버에는 `DELETE /reminders/subscribe` 가 처음부터 있었는데 **화면이 한 번도 부르지
않았다.** 기기를 바꾸거나 잘못 켠 사람은 브라우저 설정까지 들어가 권한을 막는 수밖에
없었다. 「이 기기 끄기」를 넣었다.

- 「이 기기에서 알림 켜기」가 요일 · 시간 아래에 있었다. **켜지 않으면 나머지를 아무리
  정해도 아무 일도 안 일어난다** — 맨 위로 올렸다
- 요일에 「매일 · 평일 · 월수금 · 주말」을 붙였다. 일곱 개를 하나씩 누르지 않아도 된다

**공지함 — 찾을 길이 없었다.**
「그때 바뀐 그거」를 찾으려면 날짜를 눈으로 훑는 수밖에 없었다. 목록은 커밋이 쌓이는
만큼 계속 늘어난다 — 지금 40건이고 줄어들 일이 없다. 찾기를 넣었다.
**제목뿐 아니라 펼쳐야 나오는 세부 내용과 scope 까지 본다** — 무엇이 바뀌었는지는
대개 제목이 아니라 그 안에 적혀 있다.

- 전부를 한 번에 쏟아내던 것을 최근 여섯 날치 + 「더 보기」로. 찾는 중이거나 갈래를
  고른 동안에는 다 편다 — 찾은 것을 또 감추면 안 된다
- 0건인 갈래도 눌렸다. 눌러봐야 「해당하는 것이 없습니다」가 나온다. 이제 안 그린다

**제보함(809줄)은 안쪽을 그대로 뒀다.** 들어가는 길만 바꿨다. 상태 필터, 못 불러온
것과 없는 것을 갈라 말하는 자리, 「이것까지 적어주시면 더 빨리 찾습니다」 같은 것이
이미 다 있다 — 8/24~25에 만든 자리라 여기서 다시 흔들 이유를 못 찾았다.

### 어제 시안에서 안 넣은 것을 다 넣었다

시안 링크 둘을 다시 열어 화면과 하나씩 맞춰봤다. **「원칙만 가져왔다」고 적어둔 자리가
실제로는 화면 하나를 통째로 안 만든 것**이었다.

#### 휴식 타이머 — 시안 A 의 큰 링

8/25 에 「큰 링(A)은 안 넣었다. C 의 옆에 붙는 배치와 자리를 놓고 부딪히는데, 그 자리에
다음 운동과 방금 저장한 세트가 들어가는 쪽이 낫다고 봤다」고 적었다. **부딪히는 게
아니라 위아래로 놓으면 되는 것이었다.** 링을 위에 크게(190px, 숫자 56px) 두고 그 아래에
방금 저장한 세트와 다음 운동을 적는다. 둘 다 들어간다.

큰 링이 필요한 이유는 이것이다 — **폰을 내려놓고 쓰는 물건**이다. 벤치에 누워 팔 뻗은
거리에서 24px 숫자는 안 읽힌다. 시안 A 의 60px 이 그래서 나온 크기다.

**프리셋 줄도 되살렸다.** 시안 A 는 쉬는 중에도 30 · 60 · 90 · 120 · 직접을 보여준다.
그런데 그대로 넣으면 안 됐다 — 링과 「90초 중」이 **둘 다 설정값(`duration`)을 보고
있어서**, 쉬는 중에 프리셋을 누르면 도는 타이머의 링이 튄다.

그러다 **이미 있던 버그**를 찾았다. `+30초`를 누르면 끝나는 시각만 늘고 설정값은
그대로라, **120초를 쉬면서 「90초 중」이라고 적고 링은 100% 를 넘겼다.**
스토어에 `runSec`(지금 도는 것이 몇 초짜리인가)을 설정값과 따로 뒀다. 프리셋은
다음 휴식의 길이를 정하고(쉬는 중에는 「다음 휴식」이라고 적는다), 링과 남은 시간은
`runSec` 을 본다.

**확인** — 스토어만 떼어 node 로 돌렸다. `start(90)` → `runSec 90`,
`+30` → `120`, 링 비율 `1.000`(예전 방식이면 `1.333`), 멈춘 채로 `+30` → `150`,
`stop` 뒤 `0`, 그동안 `duration` 은 90 그대로.

#### 휴식 타이머 — 시안 C 의 「다음 운동 · 기록하고 다음」

시안 C 의 본 화면에는 링 아래에 **다음 운동 카드**가 있다. 이름 · 무게 · 세트 · 횟수
세 칸 · 「기록하고 다음」 하나. 이걸 안 넣고 예전 폼을 그대로 뒀었다.

쉬는 동안 화면에 있어야 할 것은 남은 시간과 **다음에 뭘 몇 개 할지**뿐이다.
운동명 · 날짜 · 자동완성까지 다 펼친 폼을 그대로 두면 쉬는 사이에 볼 것이 아니라
지나칠 것이 된다. 그래서 **쉬는 중에는 타이머가 맨 위로 오고, 폼이 이 카드 한 장으로
줄어든다.** 값은 이미 루틴 자동 채우기가 넣어둔 그것이라 새로 짜지 않았다 —
같은 상태를 더 적은 칸으로 보여주는 것뿐이다. 「다른 운동 적기」를 누르면 원래 폼으로
돌아간다.

#### 인바디 — 시안 A 는 원칙이 아니라 화면이었다

8/25 에 「A(숫자만)의 원칙을 바탕에 깔고」라고 적었다. 성별을 안 고르면 범위를 안
그린다는 규칙 말이다. 그런데 **시안 A 는 화면이기도 했다** — 체중 · 체지방률 ·
골격근량 · 체수분 · BMI 다섯 줄을 지난 기록과의 차이와 함께 세운 표다.

눈금(B)이 그리는 것은 셋뿐이고 그나마 성별을 골라야 그린다. 그래서 **성별을 안 고른
사람은 체중도 체수분도 아무 데도 안 나왔다.** 판정 없이 숫자만 보고 싶은 사람이 볼
것이 없었다는 뜻이다 — A 를 골랐을 사람이 정확히 그 사람인데.

- 다섯 줄 표를 눈금 **위에** 세웠다. 값 옆에 지난 기록과의 차이를 적는다.
  늘고 줆에 좋고 나쁨을 안 매기고 방향만 색으로 나눈다 (BodyChange 와 같은 규칙)
- 성별을 안 골랐으면 시안 A 의 말을 그대로 한다 — **「판정은 하지 않습니다」**.
  범위를 안 그리는 것이 빠뜨린 것이 아니라 **말할 수 없어서**라는 것을 밝힌다.
  「해석은 인바디 기계의 출력지나 전문가에게 맡깁니다」까지 적었다

#### 인바디 — 시안 C 의 「그동안 운동은」

시안 C 아래에 **「그동안 운동은 — 3개월간 38회 · 주 3.0회 · 총 볼륨 142톤」**이라는
줄이 있었는데 안 넣었었다. **몸이 달라진 것과 그동안 한 것을 같은 화면에서 봐야 무슨
일이 있었는지가 이어진다** — 체중이 3kg 줄었다는 말 옆에 「38회」가 있는 것과 없는
것은 다르다.

고른 기간(지난번 · 3개월 · 처음부터)에 맞춰 그 사이의 운동을 센다. 여기서도 좋고
나쁨은 안 매긴다 — 며칠 나와서 몇 번 적었고 얼마를 들었는지만. 볼륨은 무게를 적은
것만 센다 (주간 요약과 같은 규칙, 그렇다고 화면에 적어둔다).

**확인** — `trainingIn` 을 떼어 node 로 돌렸다. 기간 밖의 기록이 안 섞이는 것,
맨몸 세트가 볼륨에서 빠지는 것, 그 기간에 기록이 없으면 `null` 을 줘서 이 줄 자체가
안 나오는 것, `buildChange` 가 준 from · to 와 맞물리는 것.

### 화면 말고 껍데기도 다시 만들었다

화면(page)을 다 돌고 나니 남은 것은 **모든 화면에 늘 얹혀 있는 것들**이었다.
여기가 제일 오래 안 본 자리였다.

#### 껍데기 — 앱에 길찾기가 네 개 있었다

`Layout` 은 560줄인데 한 번도 다시 만든 적이 없다. 세어보니 **같은 곳으로 가는 길이
네 벌**이었다.

1. 아래 탭바 다섯 (홈 · 기록 · 인바디 · 루틴 · 더보기)
2. 더보기 시트 일곱
3. **오른쪽 아래에 떠 있는 원형 버튼 안의 「카테고리별 전체 메뉴」 열한 줄**
   (홈 / 운동 / 기록·분석 / 도움 / 관리)
4. 홈의 바로 가기

오늘 아침 홈에서 ④를 정리한 것과 **정확히 같은 문제**가 ③에 그대로 있었다.
게다가 ③은 **프로필 자리**다 — 사진 · 닉네임 · 비밀번호를 손보는 곳에 앱 전체 메뉴가
들어가 있었다.

- **떠 있는 56px 원형 버튼을 없앴다.** 머리에 이미 아바타와 닉네임이 있는데, 계정을
  손보려면 화면 오른쪽 아래의 다른 버튼을 눌러야 했다. **같은 사람에 대한 것이 두
  자리에** 있었고, 떠 있는 쪽은 목록 마지막 줄과 카드 버튼 위를 늘 가렸다.
  왼쪽 아래에는 「맨 위로」가 또 떠 있어서 **화면 아래 양쪽 모서리가 다 막혀 있었다**
- 이제 머리의 아바타를 누르면 그 아래로 **내 계정** 시트가 열린다.
  안에는 사진 · 닉네임 · 비밀번호 · 로그아웃뿐이다. 길찾기는 없다
- **머리를 줄였다.** 52px 로고 + 36px 워드마크 + 「Forge Your Body · Break Your Limits」
  태그라인이 **모든 화면 위에** 있었다. 앱 이름은 매일 오는 사람이 이미 알고,
  태그라인은 고객센터 소개에 있다. 한 줄로 줄였다
- **이미 로그인한 사람에게 「로그인」 버튼을 주고 있었다.** 프로필 메뉴 아래에
  「로그인 | 로그아웃」이 나란히 있었는데, 로그인 쪽을 누르면 로그아웃도 없이 로그인
  화면으로 갔다. 없앴다. 로그아웃은 머리에도 또 있었는데 한 곳으로 모았다
- 「STEEL BODY 회원」이라고 적힌 줄을 없앴다 — 여기 온 사람은 자기가 회원인 걸 안다
- **바깥을 눌러 닫는 방식을 바꿨다.** 예전에는 `document` 의 mousedown 을 듣고 시트
  밖이면 닫았는데, 시트를 머리 아래로 옮기면 그 방식이 깨진다 — 아바타를 눌러 닫으려
  하면 mousedown 이 먼저 닫고 click 이 다시 열어 **영영 안 닫힌다.** 뒤에 판을 깔았다
- **로그아웃 키 목록이 두 곳에 손으로 나열돼 있었다.** 8/25 에 죽은 게임 키를
  정리하면서 「나열은 한 군데에만 있으면 된다」고 적어놓고 이 둘을 못 봤다.
  `authStore` 의 `LOGOUT_KEYS` 한 곳으로 모았다

#### 미션 — 열두 개 중 서로 다른 것을 세는 것은 여섯뿐이었다

8/25 에 게임 층을 걷어내며 「남은 것은 **주간 미션** 하나다」라고 적어둔 자리다.

일일의 「운동 1회」와 「3회」는 **같은 수**(오늘 기록 수)를 본다. 주간의 「3일」과
「5일」도 같은 수를 보고, 도전의 50 · 100 · 300회도 그렇다. 그래서 「이번 주 3일」을
채우는 순간 옆의 「5일」이 이미 60% 차 있는 채로 서 있었다 — **채운 것과 안 채운 것이
같은 값으로 나란히** 있는 화면이다. 게다가 열두 줄이 홈에 통째로 펼쳐져 있었다.

갈래마다 **다음에 닿을 것 하나**만 내놓는다. 문턱이 여러 개인 미션은 자연히 하나만
보인다 — 3일을 채우면 그다음은 5일 하나다. 다 보고 싶으면 갈래를 눌러 편다.
**열두 줄이 세 줄이 됐다.**

- 「도전 미션」은 300회짜리다. 매일 닦달할 말이 아니라서 이름을 「길게 보는 것」으로
  바꾸고, 색도 지운 게임이 쓰던 금색(`#ffd700`) 대신 토큰을 쓴다
- 남은 개수를 적는 줄이 **9px** 이었다. 앱의 다른 곳은 11px 아래로 안 내려간다
- 오늘 미션이 세던 변수 이름이 `parts` 였는데 실제로 세는 것은 **운동 이름**이다.
  이름이 거짓이면 다음에 여는 사람이 부위별 미션인 줄 안다

#### 관리자 「해킹 보안」 — 이 화면은 아무것도 안 보여주고 있었다

오늘 찾은 것 중 제일 나쁘다. 서버의 `/security/logs` 는 **로그 배열**을 그대로 주는데
화면은 그걸 객체로 받아

```js
const { logs = [], securityScore = {}, threats = {} } = data;
```

라고 풀고 있었다. 배열에서 그런 이름을 꺼내면 전부 `undefined` 라 기본값이 들어간다.
그래서 로그 100건이 도착해도 **언제나 「보안 로그가 없습니다」**였고, 오늘 로그인 실패 ·
차단된 요청 · 의심스러운 활동은 **언제나 0**, SECURITY SCORE 는 **언제나 0/100 에
빨간색**이었다.

**8/24 에 대시보드에서 고친 것과 같은 종류다.** 그때 「화면은 `jwt.expiry` 를 읽는데
서버는 `jwtAccessExpiresIn` 을 보낸다」를 고쳤는데, 로그 쪽은 안 봤다.

- **100점 만점 점수와 보안 체크리스트를 없앴다.** 서버에 그런 값이 없다 — 화면이 혼자
  지어내던 것이다. 인바디에서 몸에 등급을 안 매기기로 한 것과 같은 이유로, 없는 근거로
  「50점」 같은 말을 하지 않는다
- 대신 **실제로 온 로그를 센다.** 로그인 실패 · 로그인 차단 · 비밀번호 재설정 · 가입을
  오늘치와 전체로. 「의심스러운 활동」처럼 무엇을 세는지 알 수 없는 이름은 안 쓴다
- 종류로 거를 수 있게 했다. **있는 종류만 그린다**
- 예전 화면은 다섯 종류만 한국어로 알고 나머지는 영문 키를 그대로 뿌렸다.
  서버가 실제로 남기는 종류를 세어보니 **열아홉**이었다 (`ai-block` · `make-admin` ·
  `security-scan` · `CRITICAL` …). 전부 이름을 붙였다
- **로그는 서버 메모리에 쌓이고 서버가 다시 뜨면 사라진다.** 화면에 그렇다고 적었다 —
  0건인 것과 기록이 날아간 것은 다르다

**확인** — 예전 코드를 그대로 node 로 돌려봤다. 서버가 4건을 보냈는데 예전 방식은
`로그 0건 / 점수 0 / 체크리스트 0 / 실패 0 / 차단 0 / 의심 0` 을 준다.
새 방식은 4건을 받고 오늘치를 제대로 가른다 (지난 날짜의 가입은 「오늘」에서 빠진다).

**같은 종류가 더 있나 훑었다.** 프론트가 부르는 관리자 API 를 서버 응답과 하나씩
맞춰봤다 — `/security/dashboard` · `/security/users` · `/security/ai-dashboard` ·
`/security/scan` · `/security/report` · `/ratings/stats` · `/reports/*` · `/faq-gaps`.
**어긋난 것은 `/security/logs` 하나였다.**

### 점검 화면 · 보안 관리 · 측정 도구 둘

부속까지 마저 훑었다. 여기서 **같은 종류의 버그를 하나 더** 찾았다.

#### 점검 화면 — 같은 말을 다섯 번 하고, 정작 「언제 끝나나」는 맨 아래에 있었다

점검 중에 사용자가 보는 유일한 화면이다. 위에서부터 이랬다 —
제목 「정기 점검 중」 → 「잠시 후 다시 이용해주세요」 → 뱃지 「점검공지」 →
소제목 「정기 서버 점검 안내」 → 문단 「더 나은 서비스를 위해 정기 점검을 진행하고
있습니다. 점검 완료 후 자동으로 서비스가 재개됩니다」 → … → 꼬리말 「점검이 끝나면
자동으로 복구됩니다」. **다섯 자리가 같은 말을 한다.**

그 아래에 점검 시간이 있고, **남은 시간은 제일 마지막**이었다.
여기 온 사람이 알고 싶은 건 그거 하나다.

- 순서를 뒤집었다. 남은 시간이 제일 크고, 그 아래 시작~끝 시각, 그 아래 사유
- 앱이 지어낸 문단을 없앴다. **사유는 관리자가 적은 그 말**이면 된다
- **진행바가 숫자와 반대로 움직이고 있었다.** 「남은 시간」 아래에 **지나간 만큼
  차오르는** 바를 뒀다 — 숫자는 줄고 바는 늘었다. 남은 만큼 줄어들게 바꿨다
- 「적어두신 기록은 그대로 있습니다」를 넣었다. 앱이 막히면 제일 먼저 드는 걱정이다
- **관리자에게 띠를 붙였다.** 관리자는 점검 중에도 앱을 쓰는데 **아무 표시가 없었다.**
  점검을 걸어두고 잊으면 자기만 멀쩡한 앱을 보면서 사용자는 막혀 있게 된다.
  이제 위에 「사용자는 지금 앱을 못 씁니다 · {끝나는 시각}까지」가 뜬다
- **1초 타이머가 언제나 돌고 있었다.** 이 컴포넌트가 앱 전체를 감싸고 있어서,
  점검이 없는 평소에도 1초마다 앱 꼭대기가 다시 그려졌다. 초를 세야 하는 것은
  점검 중일 때뿐이라 평소에는 30초로 늦췄다

#### 보안 관리 — 가입일 열이 언제나 「-」였다

**오늘 고친 보안 로그와 같은 종류다.** 서버가 주는 이름은 `created_at` 인데 화면은
`user.createdAt` 을 읽고 있었다. 그래서 표의 **가입일이 전부 「-」**였다.
바로 위 「오늘 가입」 숫자는 서버가 `created_at` 으로 세서 맞게 나오니,
**숫자는 맞는데 열만 비어 있는** 상태였다.

**같은 종류가 더 있나 앱 전체를 훑었다.** 프론트가 서버 값에서 카멜케이스 이름을
읽는 자리를 전부 뽑아 서버 응답과 맞춰봤다. 걸린 것은 오늘 고친 둘뿐이다
(`/security/logs` 의 모양, `user.createdAt`).

그 김에 화면도 다시 짰다.

- **가입자 목록을 맨 위로.** 여기 오는 이유는 거의 사람을 찾아 막거나 풀거나 권한을
  주려는 것인데, JWT 만료 · Rate Limit · Helmet · Node 버전 · CORS · Body 한도
  여섯 카드를 다 지나야 목록이 나왔다. **서버 설정은 배포할 때 한 번 보는 것**이고
  목록은 올 때마다 보는 것이다. 설정은 접어서 아래로 내렸다
- **찾기와 역할 거르기를 넣었다.** 표를 통째로 뿌리기만 해서 사람이 늘면 못 찾는다
- 제목이 `SECURITY DASHBOARD` · `USER LIST` 영문이었다. 앱의 다른 모든 화면이
  한국어고 관리자 탭 이름도 「보안 관리」다
- 관리자 역할 색이 `#ffd700` 이었다 — 지운 게임이 쓰던 금색이다. 토큰으로 바꿨다

#### 어깨 측정 — 몸에 이름표를 붙이고 「개선 필요」라고 했다

8/25 에 인바디에서 **A·B·C·D 등급과 「개선이 많이 필요해요」를 걷어냈는데**,
같은 말이 여기 그대로 있었다.

- 어깨 너비에 이름표: 「좁은 어깨」 · 「보통 어깨」 · 「광배 어깨」 · **「문짝 어깨」**.
  게다가 제일 넓은 쪽에 **danger 색(빨강)**을 칠했다 — 넓으면 위험하다는 뜻으로 읽힌다
- 어깨:허리 비율에 **「역삼각형 (이상적)」 · 「좋은 비율」 · 「개선 필요」**.
  함수 이름부터 `getRatioGrade` 였다
- **키도 성별도 안 받는다.** 어깨 42cm 는 키 160 과 185 에서 전혀 다른 값이다.
  인바디에서 「성별을 안 받으면서 판정했다」고 지적한 것과 **같은 구조**다

재는 도구는 재기만 한다. 이름표와 등급을 없애고 **숫자와 변화만** 남겼다.
비율이 무엇을 나눈 값인지는 적어두되 어느 값이 좋다고는 말하지 않는다 —
「내 지난 값과 견주세요」까지가 이 화면이 할 수 있는 말이다.
변화량 색도 늘면 초록 · 줄면 빨강이던 것을 **방향만 가르는 색**으로 바꿨다
(인바디 「얼마나 달라졌나」와 같은 규칙).

#### 심박수 존 — 안 쓰는 값을 물어보고 있었다

「안정시 심박수 (선택)」 칸을 받아놓고 **아무 데도 쓰지 않았다.** 적어 넣어도 화면이
하나도 안 바뀐다. 안정시 심박수는 존을 재는 데 쓰라고 있는 값이다.

- 적어주면 **카보넨 식**(여유 심박 = 최대 − 안정)으로 계산한다. 안 적으면 예전처럼
  최대치에 비율을 곱한다. **어느 식으로 계산했는지 화면에 적는다**
- `220 − 나이` 를 「최대 심박수」라고 크게 띄우고 있었다. 이건 **사람마다 10~12bpm 쯤
  어긋나는 어림식**이다. 어림값이라고 적고, **재본 적 있으면 그 값을 넣는 칸**을 줬다
- 존 이름과 구간은 그대로 뒀다 — 널리 쓰는 구분이고 여기서 새로 지어낼 이유가 없다

**확인** — 카보넨 계산을 node 로 돌렸다. 최대 195 · 안정 65 에서 존2 가 143~156
(안정치 없이 곱하면 117~137), 존1 최저가 안정치보다 높고, 존5 최고가 최대치와 같다.

### 마지막으로 관리자 쪽 — 여기서 오늘 제일 무거운 것이 나왔다

#### 앱이 사용자에게 「계정이 삭제되었습니다」라고 거짓말하고 있었다

8/21 과 8/24 에 **자동 판정에서 계정 삭제를 떼어냈다.** 판정이 틀렸을 때 되돌릴 방법이
없는 동작이라서다. LEVEL 4 는 그때부터 **영구 정지 + 로그인 차단**이고 운동 기록은
그대로 남는다. `executeLevel4` 주석에 그렇게 적어뒀다 —
「지우는 것은 관리자가 화면에서 확인하고 직접 한다」.

**그런데 사람에게 하는 말을 안 바꿨다.**

`generateAiReason` 의 판정문 일곱 자리가 그대로 이렇게 말하고 있었다 —

- 「서비스 보안을 심각하게 위협하는 행위로, **즉시 계정이 삭제되었습니다**」
- 「**즉시 계정이 삭제되었습니다. 복구할 수 없습니다**」 (인젝션 · 누적 정지)
- 「즉시 계정이 삭제되었습니다」 (토큰 위조 · 무단 접근 · 관리자 API · 정지 우회)

정지된 사람이 요청을 보낼 때마다 나가는 응답도 이랬다 —
「**보안 정책 위반으로 계정 및 모든 데이터가 삭제되었습니다. 이 결정은 되돌릴 수
없습니다**」.

**지우지도 않고서 지웠다고 통보하면, 되돌릴 수 있는 사람이 포기하고 떠난다.**
자동 판정은 틀릴 수 있어서 지우는 것을 그만둔 건데, 말로는 여전히 지웠다고 하고 있으니
그 결정이 아무 의미가 없었다. 여덟 자리를 실제 동작에 맞춰 고쳤다 —

> 로그인이 영구히 막혔습니다. **적어두신 운동 기록은 지우지 않았습니다** —
> 잘못 걸렸다고 생각되시면 고객센터 제보함으로 알려주세요. 확인해서 되돌립니다.

「스팸 데이터는 자동 삭제되었습니다」도 사실이 아니라 고쳤다 (지우는 코드가 없다).

**관리자 화면도 같은 거짓말을 하고 있었다.** 「AI 관리자」의 기능 목록에
「XSS/SQL 인젝션 → **즉시 계정 삭제** (LEVEL 4)」 · 「정지 2회 누적 → **영구 삭제**」라고
적혀 있었고, 위협 카드 라벨도 **「L4 삭제」**였다. 관리자가 이 목록을 보고 판단한다.
실제로 하는 것으로 고치고, 맨 위에 **「계정과 기록을 지우는 일은 자동으로 하지
않습니다」**를 적어뒀다.

#### 점검 예약이 아예 안 되고 있었다 — 역슬래시 두 개 때문에

`MaintAdmin` 의 날짜 검사가 이랬다.

```js
if (!/^d{4}-d{2}-d{2}$/.test(dateStr)) { toast('날짜와 시작 시간을 확인해 주세요'); return; }
```

`\d` 가 아니라 **`d`** 다. 이 식은 숫자가 아니라 **글자 d 를 네 개** 찾는다.
그래서 `2026-08-27` 같은 진짜 날짜는 전부 걸러지고, 통과하는 문자열은 `dddd-dd-dd`
뿐이었다. **서버 점검과 긴급 점검을 날짜로 잡는 것이 아예 안 됐다** — 무엇을 넣어도
「날짜와 시작 시간을 확인해 주세요」만 떴다.

에러도 안 나고 빌드도 통과한다. 눌러봐야 안다.

**같은 것이 더 있나 코드 전체를 훑었다.** 정규식 리터럴을 뽑아 문자클래스 밖에
역슬래시 없는 `d{n}` · `w+` · `s+` 가 있는지 118개 파일을 검사했다. **이 하나뿐이었다.**

#### 점검 관리 — 사용자 전부를 막는 단추에 확인이 없었다

- **확인 없이 바로 걸렸다.** 게다가 세 폼의 기본 시각이 「지금」이라 화면을 열자마자
  누르면 그 자리에서 앱이 닫힌다. 이제 무엇이 일어나는지 적어놓고 한 번 묻는다 —
  「이 시간 동안 관리자를 뺀 모든 사람이 앱을 못 씁니다. 적어둔 기록은 그대로 있고,
  끝나면 저절로 열립니다」
- **지우기도 확인 없이 지웠다.** 돌고 있는 점검을 지우면 그 자리에서 앱이 열리고,
  예약된 것을 잘못 지우면 아무 일도 안 일어난다 — 둘 다 조용히 벌어진다
- 긴급 점검 요약에 **「· 강제 로그아웃」**이라고 적혀 있었다. 점검은 화면을 막을 뿐
  로그아웃시키지 않는다 (토큰을 그대로 둔다). 화면이 안 하는 일을 적고 있었다
- **목록의 아이콘이 언제나 🔧** 였다. 긴급(🚨)으로 잡은 것도 정기와 똑같이 보여서,
  무엇을 걸어뒀는지 목록만 보고는 알 수 없었다
- **지금 걸려 있는 것에 「지금 도는 중」**을 붙였다. 어느 것 때문에 앱이 막혔는지
  알 수 있어야 한다. 판단은 `MaintenanceScreen` 의 `runningNow` 하나만 쓴다 —
  두 곳에 적으면 언젠가 갈라진다
- **같은 폼을 세 번 복붙**해뒀다 (날짜 · 시작 · 소요 · 사유 · 요약 · 버튼).
  다른 것은 색 · 아이콘 · 기본값뿐인데 450줄 중 200줄 가까이가 복사본이었다.
  한 곳에 적어두고 세 번 그린다

**확인** — `runningNow` 를 떼어 node 로 10가지를 돌렸다. 매일/요일 지정/하루짜리,
자정을 넘기는 창(8/26 23:30 +60분이 8/27 00:15 에 아직 도는 것), 다른 날짜 항목이
안 걸리는 것, 옛 「즉시 시작」 찌꺼기(type 만 있고 date 없음)가 안 되살아나는 것까지
전부 통과. 날짜 검사식도 node 로 확인했다 — 옛 식은 `2026-08-27` 을 거부하고
`dddd-dd-dd` 만 통과시킨다.

### 부속까지 — 같은 말을 네 군데에 복붙해둔 자리들

#### BMI 등급이 네 군데에 복붙돼 있었다

8/25 에 「몸에 등급을 매기지 않는다」고 정하고 눈금(`data/bodyRanges.js`)을
「낮음 · 일반적인 범위 · 다소 높음 · 높음」으로 고쳤다. 그런데 **같은 판정이 앱 안에
네 군데 복붙돼 있었고 눈금 하나만 고쳤다.** 나머지 셋은 그대로 「저체중 · 정상 ·
과체중 · **비만**」이라고 말하고 있었다.

- 인바디 입력 폼 (오늘 오전에 고침)
- **인바디 목록 카드** — 같은 화면 위쪽은 「일반적인 범위」, 아래 목록은 「비만」
- **비교 화면** — 8/25 에 다시 만든 화면인데 여기도 남아 있었다

이제 넷 다 눈금 하나를 본다. 복붙을 지웠으니 다음에 기준을 바꾸면 한 곳만 고치면 된다.

#### 비교 화면이 체중이 늘면 초록, 줄면 빨강이라고 했다

「비교」의 변화량 색이 항목마다 `reverse` 를 받아 **좋은 쪽 초록 · 나쁜 쪽 빨강**으로
칠하고 있었다. 그런데 **체중은 `reverse={false}`** 였다 — 늘면 초록, 줄면 빨강이라는
뜻이다. **빼려고 오신 분에게는 정확히 거꾸로 말하고 있었다.**

인바디 「얼마나 달라졌나」는 8/25 에 이미 좋고 나쁨을 안 칠하기로 했는데, 같은 앱의
「비교」가 반대로 하고 있었다. **방향만** 색으로 나눈다 (늘면 강조색, 줄면 파랑).

#### 측정 도구 일곱 — 날짜를 받는 것이 하나뿐이었다

- **날짜 칸이 있는 것은 어깨 측정 하나뿐**이었다. 전신 사이즈 · 체력 테스트 · 유연성은
  칸이 없어서, **어제 잰 것을 오늘 적으면 오늘 날짜로 들어갔다** (화면이 date 가 없으면
  오늘을 넣는다). 셋 다 날짜를 받게 했다. 1RM 은 그대로 뒀다 — 지금 계산해서 그 자리에
  저장하는 것이라 오늘이 맞다
- **지울 수 없는 것이 셋이었다.** 측정 화면에 삭제가 이미 있는데 1RM · 체력 테스트 ·
  유연성에는 안 넘겨줘서, 한 번 잘못 적으면 영영 남았다. 다섯 도구가 이제 다 지워진다
- 체력 테스트와 유연성은 **최근 3건만** 보여주고 끝이었다. 넷째부터는 **볼 수도 지울 수도
  없었다.** 「더 보기」를 붙였다

#### 껍데기 — PC 에서 워드마크가 두 개였다

PC 는 왼쪽에 200px 사이드바가 서고 그 안에 STEEL BODY 가 크게 있다. 오늘 아침 머리를
줄이면서 거기에도 워드마크를 남겨뒀는데, 둘이 **같은 높이에 나란히** 놓인다.
PC 는 사이드바가 이름과 길찾기를, 머리가 계정을 맡는다. 사이드바의 `MORE` 도
「더보기」로 바꿨다 — 앱의 다른 모든 글자가 한국어다.

### 실패해도 「완료」라고 말하던 자리들

#### 루틴을 고칠 수가 없었다

**만들고 지우는 것만 있었다.** 운동 하나를 빼거나 세트 수를 바꾸려면 루틴을 통째로
지우고 다시 만들어야 했다 — **매일 쓰는 것인데** 그렇다.

서버에는 `PUT /my-routines/:id` 가 처음부터 있었고, 화면에서 그걸 부르는 곳은
「루틴에 운동 하나 더 넣기」 하나뿐이었다. 루틴 카드에 「수정」을 붙이고, 만들기 폼을
그대로 다시 쓴다 (제목만 「루틴 고치기」로 바뀐다).

#### 저장에 실패해도 「저장됐습니다!」가 먼저 번쩍였다

루틴 저장이 이랬다.

```js
saveMyRoutine(filtered);              // async 인데 await 이 없다
setShowCreate(false);
toast('나만의 루틴이 저장됐습니다!');   // 결과를 모르고 띄운다
```

토스트 자리는 하나라 나중 것이 앞 것을 덮는다. 그런데 **부르는 쪽 것이 먼저** 뜬다 —
서버가 거절해도 「저장됐습니다!」가 한 번 번쩍이고 나서 「실패했어요」로 바뀐다.
게다가 **폼은 이미 닫혀서 쓰던 것이 사라진 뒤**다. 삭제도 같은 모양이었다.

**같은 모양이 더 있나 코드 전체를 훑었다.** await 도 `.then` 도 없이 함수를 부르고
바로 다음 줄에서 성공을 알리는 자리를 89개 파일에서 찾았다. 여섯 자리가 나왔다.

- **점검 스케줄 추가 · 수정 · 삭제 · 예약** (네 자리) — 여기가 제일 나쁘다.
  「점검 시작!」을 보고 나갔는데 실제로는 안 걸려 있으면 **아무도 모른다**.
  이제 서버가 받아준 뒤에 알리고, 실패하면 폼도 안 닫는다
- **1RM 저장** — 측정 화면이 이미 알리는데 여기서 또 띄워서 토스트가 두 번 떴고,
  실패해도 「저장!」이 먼저 나왔다
- **비교 화면의 사진 삭제** — 올릴 때는 「이 기기에만 저장됐어요」라고 정직하게
  말하면서, 지울 때는 서버 실패를 삼키고 「삭제!」만 띄웠다. 서버에 남아 있으면
  **다음에 열 때 사진이 되살아난다**

남은 네 자리는 확인해보니 문제가 없었다 (`await` 뒤의 로컬 저장, 타이머 종료음).

#### 고객센터에서 찾을 수가 없었다 — 그리고 「못 찾은 말」이 덜 쌓이게 됐다

「자주 묻는 것」이 목록만 펼쳐져 있고 **찾는 칸이 없었다.** 지금은 두 개뿐이라 티가
안 나지만, 늘어나면 훑어야 한다.

더 중요한 것은 이것이다. 관리자 화면의 **「못 찾은 말」은 실제로 물어본 말이 쌓여야**
쓸모가 있는데, 그걸 모으는 자리가 **제보함 안의 「무엇이 궁금하세요?」 한 곳뿐**이었다.
그런데 오늘 고객센터를 다시 만들면서 **갈래를 밖에서 고르게** 해서, 그 자리를 건너뛰는
길이 생겼다. 모으는 자리를 줄여놓고 「배포되면 쌓인다」고 할 수는 없다.

「자주 묻는 것」에 찾기를 붙이고, **여기서도 답이 없는 말을 남긴다.** 규칙은 제보함
쪽과 같다 — 2초 멈춘 뒤에 보내고(치는 동안 스치는 글자는 안 보낸다), 같은 말은 한 번만,
친 말만 남기고 누가 쳤는지는 서버도 안 남긴다.

찾아도 안 나오면 「무엇을 찾으셨는지는 남겨뒀습니다 — 같은 것을 여러 분이 찾으시면
여기에 올려둡니다」라고 적고 바로 물어볼 길을 준다.

**확인** — `matchFaq` 를 떼어 node 로 돌렸다. 「기록」 2건 · 「정지」 1건 ·
「차단」(적힌 말이 아니라 사람들이 쓰는 말) 1건이 걸리고, 한 글자와 없는 말은 0건이다.

#### 받아놓고 안 쓰는 값이 더 있나

심박수 존에서 「안정시 심박수」를 물어보고 버리던 것을 찾은 김에, `useState` 로 만든
값이 **setter 말고는 한 번도 안 읽히는** 자리를 89개 파일에서 훑었다. **없었다.**

### 홈트 — 5번째에서 전화를 받으면 다섯 개를 다시 해야 했다

타이머 화면의 「중지」가 `running` 만 끄고 끝이었다. 그런데 다시 「시작하기」를 누르면
`beginPhase(0, false)` 라 **처음부터** 돈다. 8개짜리를 하다가 5번째에서 멈추면
**앞의 다섯 개를 다시 해야 했다.** 홈트는 집에서 폰 놓고 하는 것이라 중간에 멈출 일이
가장 잦은 화면인데 그렇다.

- 「중지」를 **「일시정지」**로 바꾸고 멈춘 자리를 기억한다. 남은 초까지 그대로 들고
  있다가 이어서 센다. 「이어서 하기 · 5번째 운동에서 멈췄어요 · 12초 남음」
- 「처음부터」와 「목록」을 따로 뒀다 — 되돌리는 것과 이어가는 것은 다른 일이다
- **중간에 그만두면 아무것도 못 남겼다.** 끝까지 해야만 「기록 저장」이 나왔는데,
  중간에 멈추는 사람이 더 많다. 「여기까지 기록하기」를 넣었다

**완료 화면이 「COMPLETE!」 한 줄이었다.** 무엇을 얼마나 했는지가 없었다.
프로그램 이름 · 운동 개수 · 움직인 시간을 적고, 「다시 하기」를 같이 뒀다.

**기록으로 넘길 때 운동명만 넘기고 있었다.** 기록 화면은 세트와 횟수가 **필수 칸**이라,
홈트를 끝내고 「기록 저장」을 누르면 빈 폼에 이름만 적힌 채 **세트와 횟수를 지어내야**
했다. 홈트는 시간으로 하는 것이니 「한 운동 = 한 세트」로 세서 미리 채운다.
기록 화면이 `state.sets` · `state.reps` 를 받게 했다.

### 제보 관리에 지운 게임이 아직 남아 있었다

관리자가 제보를 펼치면 나오는 기기 정보가 이렇게 그려지고 있었다.

```js
r.device.appVersion && ('v' + r.device.appVersion),
r.device.level && ('LV ' + r.device.level),
r.device.tickets && ('🎫 ' + r.device.tickets),
```

8/25 에 레벨과 티켓을 걷어내면서 **보내는 쪽**(제보함)과 **서버**(`DEVICE_FIELDS` 를
`appVersion` · `browser` 둘로 줄임)는 고쳤는데, **받아서 그리는 이 자리만** 그대로였다.
오는 값이 없으니 화면에는 안 보였다 — 지운 기능을 아직 기다리고 있던 코드다.

**앱 전체를 훑어 남은 게임 흔적을 다시 셌다.** `level` · `tickets` · `EXP` · `칭호` ·
`파칭코` 가 나오는 자리를 전부 뽑아보니, 남은 것은 전부 다른 뜻이었다 —
욕설 판정 등급(`abuse.level`), AI Guard 위협 등급(L1~L4), 그리고 앱이 뜰 때 죽은 키를
쓸어내는 목록(`REMOVED_GAME_KEYS`). **게임 층은 이제 프론트에 한 줄도 없다.**

### 공지 아홉 건을 셋으로 묶었다

하루에 아홉 건을 올렸더니 고객센터의 「최근 바뀐 것」 여섯 줄이 **전부 오늘 것**이 됐다.
읽는 사람에게 필요한 것은 「오늘 무엇을 했나」가 아니라 **「나에게 무엇이 달라졌나」**다.
갈래를 셋으로 잡았다 —

1. **앱의 모든 화면을 다시 만들었습니다** (무엇이 어떻게 바뀌었나)
2. **앱이 잘못 알려드리던 것들을 고쳤습니다** (사과. 정지 안내 · 체중 변화 색 · BMI ·
   「완료」 거짓말 · 안 쓰는 입력칸)
3. **못 하던 것들을 할 수 있게 했습니다** (루틴 수정 · 홈트 이어서 하기 · 알림 끄기 ·
   측정 날짜와 지우기)

**사과는 따로 세웠다.** 다시 만든 이야기 속에 섞어 넣으면 「많이 고쳤습니다」로 읽힌다.
「계정이 삭제되었습니다」를 받고 기록이 사라진 줄 알았던 사람이 있으면, 그 사람이 찾을 수
있는 자리에 그 말만 있어야 한다.

### 서버가 영어로 말하고 있었다

프론트는 서버가 준 `error` 문구를 **그대로 토스트에 띄운다.** 그런데 서버 쪽에
`Invalid token` · `User not found` · `Account blocked` · `Too many requests` 처럼
영문이 열네 자리 남아 있었다. 앱의 다른 모든 글자는 한국어다.

게다가 **무엇을 해야 하는지가 안 적혀 있었다.** 「Invalid token」을 본 사람이 할 수 있는
일은 없다. 「로그인 정보가 올바르지 않아요. 다시 로그인해주세요」로 바꿨다.

프론트가 이 문구를 **글자로 비교하는 곳이 있나 확인했다** — 없다. 상태 코드(401)만 본다.

### 관리자 — 되돌릴 길이 없던 것 둘

- **보안 검사가 왜 걸렸는지를 버리고 있었다.** 서버는 `detail` 로 「production 이 아님:
  development」처럼 이유를 같이 보내는데, 화면은 이름과 `VULN` 만 그렸다. 무엇을 고쳐야
  하는지 알 수 없다. 이유를 붙이고, 걸린 것을 위로 올렸다 — 통과한 것 스무 줄 사이에
  섞어두면 못 찾는다
- **욕설 기록의 「확인함」을 되돌릴 수 없었다.** 실수로 누르면 목록에서 흐려지고
  「확인 안 함」 수에서도 빠지는데, 서버는 `reviewed:false` 를 받으면서 화면에 그 단추가
  없었다. 사람이 판단하는 자리라 되돌리기가 있어야 한다

### 측정 기록만 꺼낼 길이 없었다

운동과 인바디는 히스토리에서 CSV 로 뽑을 수 있는데 **측정만 없었다.** 전신 사이즈를
1년 재둔 사람이 그것만 못 꺼낸다. 고객센터의 「기록이 사라지면」 답이
「서버에 있습니다」인데, 꺼낼 길은 두 가지뿐이었던 셈이다.

종류마다 칸이 다르다 — 둘레 아홉 개 · 1RM 세 개 · 체력 여섯 개 · 유연성 네 개.
넓은 표로 만들면 **빈 칸이 대부분인 서른 열짜리**가 된다. 한 줄에 한 항목으로 길게 폈다
(`날짜, 종류, 항목, 값`). 엑셀에서 피벗으로 돌리기도 이쪽이 쉽다.

`arm_l` 같은 내부 이름 대신 **화면에 적힌 이름 그대로** 내보낸다 — 파일을 열었을 때
무슨 뜻인지 몰라야 할 이유가 없다.

**확인** — 만드는 부분만 떼어 node 로 돌렸다. 빈 값과 null 이 빠지는 것, `date` 가 첫 칸에
이미 있으니 두 번 안 적히는 것, 따옴표가 든 값(`플랭크, "최대"`)이 제대로 감싸지는 것.

### 확인을 그때그때 버리지 않기로 했다 — `npm run check`

이 앱에는 테스트 틀이 없다. 그동안 **「로직만 떼어 node 로 돌리기」**로 확인해 왔는데,
그때마다 임시 파일을 만들고 지웠다. 같은 것을 다음에 또 짜야 한다.

오늘 특히 그럴 이유가 생겼다. **화면 여럿이 같은 계산 한 곳을 보게** 만들어놨다 —
볼륨(`volumeOf`) 하나를 고치면 홈 · 기록 · 인바디가 같이 바뀌고, BMI 눈금 하나를 고치면
인바디 폼 · 목록 카드 · 비교 · 신체 분석 **네 화면**이 같이 바뀐다. 한 곳을 만졌을 때
어디가 흔들리는지 손으로 확인할 수 있는 크기가 아니다.

`frontend/scripts/check-data.cjs` 로 남겼다. 지금 17가지를 본다 —

- **볼륨** — 무게 있는 것만 세는지, `20kg 양쪽` 같은 자유 입력에서 첫 숫자를 읽는지
- **BMI 눈금** — 네 구간 이름이 맞는지, 그리고 **「비만」이라는 말이 눈금에 없는지**
- **여성 체지방 22%** — 「일반적인 범위」로 나오는지 (8/25 에 고친 핵심이다),
  성별을 안 고르면 눈금이 `null` 인지
- **최고 기록** — 70kg 12회가 80kg 5회보다 세게 나오는지, 맨몸을 무게로 안 세는지
- **그동안 운동은** — 기간 밖이 안 섞이는지, 맨몸이 볼륨에서 빠지는지,
  기록이 없으면 `null` 을 줘서 그 줄 자체가 안 나오는지
- **부위** — 아는 것과 모르는 것

빌드가 못 잡는 것들이다. 빌드는 **모양**만 보고, 이건 **말이 맞는지**를 본다.

## 그 자리에 다섯 가지를 새로 넣었다

지운 것으로 끝내지 않기로 했다. 시안으로 다섯 개를 그려서 고르시게 했고, 전부 하기로 했다.
**작고 확실한 것부터** — D → B → E → C → A 순으로 붙였다.

### D · 최고 기록을 넘기면 그 자리에서 짚어준다

기록을 쌓기만 하고 「늘었다」고 말해주는 데가 없었다. 파칭코와 레벨이 요란했던 자리라
더 그랬다. 이제 저장할 때 한 번 견줘서, 자기 최고를 넘었으면 저장 직후에 띠로 알린다.

**무게만 보면 틀린다.** 70kg 12회가 80kg 5회보다 세다 — 1RM 으로 환산해서 견준다.
식은 측정 시스템의 1RM 계산기에 이미 있던 것이라, 두 곳에 따로 적지 않고
`data/personalRecord.js` 한 곳으로 모아 양쪽이 같은 것을 읽게 했다.

- 크게 보여주는 것은 **실제로 든 무게**다. 환산값은 왜 경신인지 밝히는 자리에만 작게 적는다
  — 75kg 8회에서 85kg 5회로 갔을 때 큰 글씨가 97 이면 무슨 소린지 알 수 없다
- 맨몸은 횟수로 센다. 무게 있는 것과 서로 견주지 않는다 (푸시업 50회와 벤치 80kg 은
  한 자에 못 올린다)
- 무게가 자유 입력이라 ('60' · '60kg' · '20kg 양쪽') 문자열에서 처음 나오는 수를 읽는다
- **그 종목의 첫 기록에는 안 뜬다.** 처음 적는 운동마다 「최고 기록」이 뜨면 그 말이 죽는다
- 같은 무게를 또 들면 경신이 아니고, 최고 기록 날짜도 먼저 세운 날에 머문다
- 기록 목록 아래에 **종목별 최고 기록**을 접어 뒀다. 60일 넘게 멈춘 종목에는 표를 단다 —
  목록의 쓸모는 무엇을 세웠나보다 무엇이 멈춰 있나에 있다

### B · 이번 주에 얼마나 했는지 한 장으로

히스토리는 달력이라 「했다 / 안 했다」만 보였다. 홈의 주간 달력 **바로 아래**에 붙였다 —
달력이 어느 날 했는지를 보여주니 여기서는 얼마나 했는지만 말한다. 같은 주를 두 번 안 그린다.

운동한 날 · 총 볼륨 · 주 연속, 지난주와의 차이, 부위 분포, 지난 4주 흐름.
할 말은 최대 두 줄이고 **없는 말은 지어내지 않는다.** 기록이 없으면 아예 안 그린다.

**볼륨은 무게를 적은 것만 센다.** 맨몸은 체중을 모른다 — 인바디 체중을 끌어다 쓰면
체중을 안 적은 사람은 0이 되고, 적은 사람은 어느 날 체중으로 셀지가 또 문제가 된다.
숨기지 않고 「맨몸 N세트는 빠져 있어요」라고 적어둔다.

**부위 사전을 새로 만들었다** (`data/bodyPart.js`). 운동명이 자유 입력이라 정해진 목록으로는
못 맞춘다. 낱말은 앱이 이미 쓰는 이름에서 뽑았다 — 루틴 추천의 여섯 부위와 운동 검색 목록.
못 맞히면 '기타' 로 두고 억지로 밀어 넣지 않는다.

겹치는 이름이 문제였다. 규칙 순서로 푸는데 더 좁은 이름이 넓은 이름 아래에 있으면
순서로는 안 풀린다 — **'레그레이즈'가 어깨의 '레이즈'에 먼저 걸렸다.** 그런 것만 예외로 뺐다
(레그레이즈 · 데드버그).

### E · 답을 못 찾고 나간 말을 모은다

FAQ 를 무엇으로 늘릴지 감으로 정했다. 고객센터의 「무엇이 궁금하세요?」에서 쳤는데
**자주 묻는 것이 하나도 안 걸린** 말만 모은다. 관리자 화면에 「못 찾은 말」 탭을 뒀다.

**친 말과 횟수, 날짜만 남긴다. 누가 쳤는지는 서버도 안 남긴다** — 무엇을 모르는지는
알아야 하지만, 누가 모르는지까지 알 이유가 없다.

화면이 알아서 보내는 값이라 조심할 것이 있었다. 치는 동안 스쳐 지나가는 글자를 다 보내면
목록이 쓰레기가 된다 — **2초 멈춘 뒤**에 보낸다. 그 정도 멈췄다는 것은 「여기에는 답이
없네요」를 읽었다는 뜻이다. 같은 말은 화면이 살아 있는 동안 한 번만 보내고, 서버는
분당 20개까지, 두 글자 미만은 안 받는다.

띄어쓰기와 기호를 지운 소문자로 같은 말을 모은다 — '비 번' · '비번' · '비.번' 이 한 줄이 된다.
관리자 화면은 지금 FAQ 로 그 말을 다시 찾아본다. 쌓일 때는 아무것도 안 걸린 말이니,
지금 걸린다면 그 사이에 답을 넣었다는 뜻이다 — 지워도 되는 줄로 표시한다.

### C · 정한 요일과 시각에 알린다

**시간대가 이 기능의 전부다.** 서버는 UTC 로 돌고 사람은 자기 시간대로 산다. 저녁 7시에
보내라는 말은 그 사람의 저녁 7시다. 설정에 브라우저의 UTC 차이를 같이 담아두고,
보낼 때마다 그걸로 현지 시각을 만들어 본다.

- 설정은 **서버가 들고 있다** — 기기를 바꿔도 그대로다
- **오래 쉬면 한 번 알린다** — 마지막 운동에서 사흘이 지나면 정한 요일이 아니어도
- **그날 이미 운동을 적었으면 안 보낸다.** 다 하고 나서 「오늘 운동하는 날이에요」는
  도움이 안 된다
- 같은 날 두 번 안 보낸다. **보내기 전에 먼저 적어둔다** — 보내는 사이에 다음 tick 이
  돌면 두 번 간다
- 기기마다 구독이 따로다. 죽은 구독(404·410)은 그 자리에서 지운다

**못 하는 것을 누를 수 있게 두지 않았다.** 서버에 키가 없으면 켜기 단추를 아예 안 그리고,
브라우저가 알림을 못 하면 그렇다고 적고, **아이폰은 홈 화면에 추가해야 온다**는 것을
미리 알린다. 한 번 막으면 앱이 다시 물어볼 수 없다는 것도 적었다.
「지금 한 통 보내보기」를 둔 이유는, 권한 · 기기 등록 · 서버 키 중 어디가 막혔는지
사람이 알 길이 없어서다.

**Render 무료 요금제는 안 쓰면 잠든다.** 잠든 동안엔 타이머도 안 돈다. 정한 시각에 아무도
앱을 안 쓰고 있었으면 그날은 건너뛴다. 늦게 보내지 않는 것은 일부러다. 화면에도 적었다.

VAPID 키는 저장소에 두지 않는다. `node backend/scripts/gen-vapid.js` 로 만들어 환경 변수로
넣는다. 키가 없으면 서버는 그대로 뜨고 스케줄러만 안 뜬다.

### A · 짜둔 루틴대로 순서를 따라간다

**루틴을 짜놔도 기록 화면과 이어져 있지 않았다.** 기록 화면에 루틴을 읽는 코드가 한 줄도
없어서, 루틴을 만들어두고도 매번 운동 이름을 처음부터 쳤다. 「루틴을 왜 만드나」에
답이 없었다.

이제 루틴 화면의 **이 루틴으로 운동 시작**을 누르면 기록 화면으로 넘어가고, 맨 위에
진행표가 붙는다. 저장할 때마다 한 칸씩 넘어간다.

- 진행표는 **서버에 있다** — 폰으로 시작해서 다른 기기로 이어갈 수 있다
- **시작할 때 루틴의 운동 목록을 베껴 담는다.** 하는 도중에 루틴을 고쳐도 하던 것이
  흔들리면 안 된다
- 폼을 미리 채우되 **지난 기록이 먼저다** — 루틴에 적힌 '4세트 10~12회' 보다 지난번에
  실제로 든 무게가 오늘 쓸모 있다. 지난 기록이 없으면 루틴 값을 쓴다
- **저장한 운동 이름이 그 칸과 다르면 칸을 안 넘긴다.** 루틴 중간에 다른 운동을 하나
  적을 수 있는데, 그걸로 칸이 넘어가면 안 한 운동이 끝난 것이 된다
- 칸을 못 넘겨도 「저장 실패」라고 하지 않는다 — 기록은 이미 저장됐다
- 마지막 칸을 끝내면 진행표를 지운다. 다 한 진행표가 계속 위에 붙어 있으면 안 된다

## 붙이고 나서 찾은 것

**연달아 저장하면 최고 기록이 잘못 떴다.** 저장 뒤 목록을 다시 받아오는 것을 기다리지
않아서, 저장 직후의 목록이 방금 넣은 것을 모르는 상태로 잠깐 남았다. 최고 기록은
「넣기 전」 목록과 견주는데 그 사이에 한 번 더 저장하면 앞의 것을 못 본다 —
**벤치 85kg 를 넣고 곧바로 82kg 를 넣으면 82kg 가 최고 기록이라고 떴다.**

**운동 검색에서 「이 운동 기록하기」로 들어오면 루틴이 그 칸을 빼앗았다.** 운동을 지정해서
들어온 것인데 진행 중인 루틴이 이겨서, 누른 것과 다른 운동이 적혀 있었다.

**홈 검색창에 한 글자 칠 때마다 기록 전체를 다시 셌다.** 성취 뱃지가 뱃지 판정 ·
최장 연속 · 한 달 개근 · 종목별 횟수를 매 렌더마다 처음부터 셌다. 기록이 쌓일수록
타자가 밀린다. 기록이 바뀔 때만 세게 하고, 뱃지와 이번 주 요약은 아예 다시 안 그리게 했다
(주간 미션은 이미 그렇게 되어 있었다 — 뱃지만 빠져 있었다).

**주 연속을 세는 데가 헛돌았다.** 한 주씩 거슬러 가며 7일을 다시 만들어 보는 방식이라
기록이 하나도 없는 사람도 5년치(260주 × 7일)를 훑었다.

## 휴식 타이머를 다시 만들었다

리메이크 대상을 정하려고 화면마다 마지막으로 손댄 때를 뽑아봤다.

시안을 셋 그렸다 — A(제자리에서 정확하게) · B(어느 화면에서나 따라온다) ·

**고친 것 셋**

1. **시간이 안 맞던 것** — 끝나는 시각을 정해두고 250ms 마다 시계를 다시 본다.

저절로 시작하는 것은 끌 수 있다. 끄면 예전처럼 직접 눌러서 시작한다.

## 인바디 「신체 분석」을 다시 만들었다

4월 15일 이후 한 번도 안 고친 화면이었다. 읽어보니 **네 가지가 근거 없이 말하고 있었다.**

1. **성별을 안 받으면서 남성 기준으로 판정했다.** 체지방률 20% 이상을 「약간 높은 편」,
   25% 이상을 「내장지방 위험」이라고 했는데 여성은 20~28%가 건강한 범위다.
   **건강한 몸을 보고 위험하다고 말하고 있었다.**
2. 몸에 **A · B · C · D 등급**을 매기고 「개선이 많이 필요해요」라고 했다.
3. **몸 그림의 팔과 다리를 서로 다른 색으로 칠했는데, 근거는 골격근 비율 숫자 하나뿐이었다.**
   같은 값으로 「팔 근육 부족」과 「하체 근육 보강 필요」를 동시에 말했다.
   인바디 값은 부위별 근육량을 모른다 — **없는 것을 그리고 있었다.** 이게 제일 나빴다.
4. 「호르몬 불균형이나 면역력 저하 위험」 같은 **의학적 단정**을 했다.

시안: https://claude.ai/code/artifact/bf41fbf4-9342-463b-9723-d766c5e6f60f

**셋 다 넣었다.** A(숫자만)의 원칙을 바탕에 깔고, B(참고 범위)를 본 화면,
C(얼마나 달라졌나)를 그 아래에 붙였다. 둘은 부딪히지 않는다 —
B 는 「지금 어디쯤인가」, C 는 「어디서 어디로 왔나」다.

**성별을 받되 필수가 아니다.** `male` · `female` · 안 알려줌 셋뿐이다. 안 고르면
체지방률과 골격근 비율의 범위를 **아예 안 그린다** — 그게 A 다. BMI 는 성별을 안 가려서
그때도 그린다. **나이는 안 받는다** — 범위를 조금 더 정밀하게 하자고 개인정보를 늘릴
이유가 없다. 서버가 들고 있어 기기를 바꿔도 다시 안 묻는다.

말도 바꿨다. 「정상 · 위험」이 아니라 **「일반적인 범위」**다. 등급을 안 매기고 몸 그림도
안 그린다. 화면에 「이 범위는 참고용입니다 — 나이 · 운동 이력 · 재는 기계에 따라
달라집니다」라고 적어뒀다.

C 는 **지난번 · 3개월 · 처음부터**로 견준다. 3개월치가 없으면 제일 오래된 것으로
떨어지되 날짜를 같이 보여준다 — 속이는 것이 아니다.

**말할 수 있을 때만 말한다.** 체중과 골격근이 둘 다 있어야 한 마디를 붙이고,
「줄어든 무게는 대부분 지방」은 체지방률까지 내려갔을 때만 붙인다.
0.2 안쪽 움직임은 재는 기계 오차로 보고 아무 말도 안 한다.

**확인** — 두 계산을 떼어 node 로 43가지를 돌렸다. 제일 중요한 것은 이것이다 —
**여성 22% 체지방이 「일반적인 범위」로 나온다.** 예전에는 「약간 높은 편」이었다.

새로 만들 필요가 없는 것이 대부분이었지만, **덜 손본 곳에서 넷이 나왔다.**

### 운동 검색 — 앱 안의 사전을 버리고 인터넷을 8초 기다렸다

한국어를 치면 영어로 바꿔서 외부 DB(wger.de)에 8초를 기다렸다. 영어 전용이라
대부분 아무것도 안 나왔고, 나와도 영어 이름뿐이라 설명이 없었다.
화면의 「최대 8초」라는 문구 자체가 그 어색함을 인정하고 있었다.

**정작 한국어 운동 사전 96개가 설명까지 달고 앱 안에 있었다.** 그런데 번역에만 쓰고
결과로는 안 보여줬다 — 좋은 자료를 버리고 더 나쁜 것을 기다린 셈이다.

순서를 뒤집었다. 앱 안의 사전을 **치는 동안 바로** 보여주고, 외부 DB 는 **눌러야**
나간다. 한국어 · 영어 · **초성**(ㅂㅊㅍㄹㅅ) · 부위 이름으로 찾고, 띄어쓰기가 달라도
찾는다. 못 찾으면 **「친 그대로 기록하기」**를 준다 — 사전에 없는 운동을 한다고 해서
기록을 못 하면 안 된다. **인터넷이 끊겨도 검색은 된다.**

카드에 할 일이 둘이라 갈랐다. 통째로 「기록하러 가기」로 두면 같은 갈래
(벤치프레스 → 인클라인 · 디클라인 …)를 볼 방법이 없어진다.

### 스톱워치도 시간을 놓치고 있었다 — 같은 버그 세 번째

`components/measure/StopwatchSection.jsx` 가 100ms 마다 100 을 더하고 빼고 있었다.
오늘 휴식 타이머에서 고친 것과 **같은 버그**다. **플랭크를 재려고 폰을 내려놓으면
정확히 그때 어긋난다.**

같은 방식이 세 곳에 있었다 — 홈트(8/24 고침) · 휴식(오늘 고침) · 스톱워치(방금).
이제 다 시계를 본다. 타이머가 끝나면 **소리로도 알린다** — 전에는 토스트뿐이라
화면을 안 보고 있으면 끝난 줄 몰랐다.

알림 소리를 두 곳에서 쓰게 돼서 `data/restAlert.js` 를 `data/alertSound.js` 로
옮기고 `beepDone` 으로 이름을 바꿨다. 휴식만의 것이 아니게 됐다.

### 미션이 없는 EXP 를 약속하고 있었다

오늘 아침에 레벨과 EXP 를 없앴는데 **미션 화면은 그대로 「+N EXP」라고 적혀 있었다.**
줄 수 없는 것을 계속 약속하고 있었다. 「N 남음」으로 바꾸고 exp 값과 안 쓰는
'보상' 라벨도 걷어냈다. 이제 코드 어디에도 EXP 가 없다.

### 소셜 로그인 넷을 고쳐놓고 버튼을 안 만들었다

서버는 구글 · 네이버 · 페이스북 · 인스타그램 **넷을 다 지원한다.** 8/24 에 네 곳의
state 등록 버그를 고쳤다. 그런데 **로그인 화면에는 구글 버튼 하나뿐이었다.**
고쳐도 누를 데가 없었다 — 「화면이 없던 기능」이 또 있었던 셈이다.

**되는 것만 그린다.** `GET /api/oauth/providers` 를 새로 두고, 서버가 쓸 수 있다고
한 것만 버튼으로 그린다. 열쇠 값은 안 돌려준다 — 설정됐는지 여부만이다.
만들면서 하나 찾았다: 인스타그램 열쇠 이름이 `INSTAGRAM_APP_ID` 인데 새로 쓴 곳에서
`INSTAGRAM_CLIENT_ID` 를 봤다. 그대로 뒀으면 설정을 해도 버튼이 영영 안 나왔다.

**실패 이유도 갈랐다.** 예전에는 무엇이 잘못됐든 「다시 시도해주세요」였는데,
열쇠가 설정 안 된 제공자는 **다시 시도해도 영영 안 된다.** 될 것처럼 말하면 안 된다.

`render.yaml` 에 네이버 · 페이스북 · 인스타그램 열쇠 자리를 만들어 뒀다.
**넣은 것만 버튼으로 나온다.**

### 안 고친 것들

홈트 · 측정 · 히스토리 · 비교 · 루틴 · 회원가입은 훑어봤지만 손대지 않았다.
API 오류 처리가 다 되어 있고, 최근에 손본 곳이고, 실제로 틀린 것을 못 찾았다.
**멀쩡한 화면을 다시 만드는 것은 리메이크가 아니라 헛일이다.**

## 남은 화면을 다 다시 만들었다

「리메이크」를 버그 고치기로 좁게 잡고 있었다. 화면을 **새로 만드는 것**을 말씀하신
거였다. 남은 화면을 하나씩 다시 만들었다.

**히스토리 — 이름값을 못 하고 있었다.** 이름도 「히스토리」고 앱 소개에도
「달력으로 되짚는다 — 빠진 날이 눈에 보여야 안 빠진다」고 적어뒀는데, 화면은
날짜별 목록이었다. **빠진 날은 아예 안 그려지니 눈에 보일 수가 없었다.**
달력을 맨 위에 세우고, 칸마다 부위를 한 글자로 적었다 (가 · 등 · 어 · 하 · 팔 · 코).
날짜를 누르면 그날만, 안 누르면 그 달 전체. 예전에는 언제나 전 기간을 쏟아냈다.
기록이 없는 달이면 「기록이 있는 달로」를 준다.

**루틴 — 매일 쓰는 것이 맨 아래에 있었다.** 오늘 「이 루틴으로 운동 시작」을
붙여놨는데 그 버튼이 추천 목록 한참 아래였다. 내 루틴을 위로 올렸다.

**홈트레이닝 — 무엇을 하는지 시작해봐야 알았다.** 이제 눌러서 미리 본다.

**측정 시스템 — 작은 탭 일곱 개가 옆으로 스크롤됐다.** 격자로 펼치고 각각
무엇을 하는 것인지 한 줄씩 붙였다. 지정해서 들어오지 않으면 목록부터 연다.

**비교 — 남의 숫자로 그래프를 그렸다.** 기록이 둘 미만이면 예시 값으로 그리는데
「예시입니다」가 그래프 **아래**에 작게 있었다. 다 보고 나서야 자기 숫자가 아니었다는
것을 알게 된다. 위로 올리고 분명히 적었다.

**회원가입 — 소셜 가입이 아예 없었다.** 소셜로 들어오면 계정이 저절로 만들어지는데
버튼이 로그인 쪽에만 있었다. 공용 컴포넌트로 빼서 양쪽이 같이 쓴다.

## 앱 전체 훑기 — 안 보던 곳

**홈트 타이머가 첫 운동만 하고 나머지를 전부 건너뛰고 있었다**

8개짜리 프로그램을 시작하면 운동 1번을 하고, 그 다음부터는 **운동 단계가 통째로 사라진 채 휴식만 이어지다** 끝났다.

- effect 두 개가 각자 `timeLeft` 를 건드리고 있었다. 휴식이 끝나 다음 운동으로 넘어가는 commit 에서 둘이 같이 돌면서 한쪽은 `휴식 시작`, 다른 쪽은 `운동 시간` 을 써 넣었다. 마지막에 쓴 값이 남아 **isRest 는 true 인데 시간은 운동 시간** 인 상태가 됐다
- 두 effect 의 deps 를 종이에 놓고 따라가도 헷갈려서, 그 로직만 떼어내 실제로 돌려봤다. `운동 A → 휴식 → (B 건너뜀) 휴식 → (C 건너뜀) 완료` 가 그대로 재현됐다
- 단계 전환을 `beginPhase` 한 곳으로 모았다. 지금 단계는 ref 에 들고, effect 는 시계만 본다
- **남은 초를 1씩 빼던 것도 고쳤다.** 그 방식은 화면을 내리거나 다른 탭을 보는 동안 브라우저가 타이머를 늦춰서, 30초 플랭크가 1분이 되고 그동안 숫자는 멈춰 있다. 끝나는 시각을 정해두고 250ms 마다 시계를 다시 본다
- 고친 뒤 다시 돌려서 `A 3초 → 휴식 2초 → B 3초 → 휴식 2초 → C 3초`, 정확히 13초에 완료되는 것을 확인했다

**네이버 · 페이스북 · 인스타그램 로그인이 100% 실패하고 있었다**

`generateState()` 는 state 문자열을 만들기만 하고, Map 에 등록하는 줄은 부르는 쪽에 있었다. **구글만 그 줄을 갖고 있었다.** 나머지 셋은 등록이 없으니 콜백의 `validateState` 가 언제나 `has(state) === false` 로 떨어져 `invalid_state` 로 튕겼다.

- 발급 안에서 등록까지 하게 바꿨다. 빠뜨릴 수 있는 자리를 없앤다
- 네 곳 모두 통과하고, 같은 state 를 두 번 쓰면 여전히 막히는 것을 확인했다 (1회용)

**보안 대시보드가 서버가 주지 않는 이름을 읽고 있었다**

화면은 `jwt.expiry` · `helmet.enabled` · `cors.origins` · `rateLimit.login.max` 를 읽는데, 서버는 `jwtAccessExpiresIn` · `helmetEnabled` · `corsOrigin` 처럼 평평한 이름으로 보냈다.

- 그래서 **JWT 만료는 빈칸, Helmet 은 `비활성화 · 위험`** (실제로는 켜져 있다), CORS 는 `없음`, Rate Limit 은 `위험` 으로 떴다. 안전한 서버를 위험하다고 보고하는 대시보드였다
- 숫자도 손으로 적어둔 값이라 실제와 달랐다. `분당 100회` 인데 `15분당 100회` 로, 로그인 제한(15분당 20회)은 아예 없는 값으로 보고했다
- `config/security.js` 를 만들어 rate limit · JWT · bcrypt · body 한도를 한곳에 뒀다. `index.js` 가 적용하고 대시보드가 같은 것을 읽는다. `auth.js` · `oauth.js` 의 `15m` · `HS256` · `12` 도 여기서 읽는다
- 판정 함수도 틀렸다. `parseInt('15m')` 를 시간으로 읽어 **15분짜리 만료를 15시간으로 보고 `주의`** 를 띄웠고, rate limit 은 창 길이를 안 보고 횟수만 봤다 (15분당 20회와 1분당 20회를 같이 취급). 단위를 보게 고쳤다
- 차단 · 관리자 부여가 실패하면 `console.error` 만 하고 화면은 그대로였다 — 사람을 차단하는 자리라 실패를 말하게 했다

**루틴에 두 번째 운동을 넣을 수 없었다**

추천 화면의 `내 루틴에 추가` 는 같은 이름의 루틴이 있으면 `이미 포함된 운동이에요` 라며 돌려보냈다. **그 운동이 실제로 들어 있는지는 보지도 않았다.** `머신 가슴 루틴` 을 한 번 만들고 나면 거기에 아무것도 더 못 넣었다.

- 고칠 길이 없었다 — 루틴을 **고치는** API 자체가 없었다. `PUT /api/my-routines/:id` 를 만들었다 (남의 루틴은 못 고친다)
- 이제 이미 있는 루틴이면 이어붙이고, 진짜로 들어 있을 때만 있다고 말한다
- 루틴 삭제가 조용히 끝나던 것, 저장 응답의 id 가 덮이던 것(`{ id, ...routine }` 순서)도 같이 고쳤다

**히스토리 · 검색 · 측정 · 미니게임**

- **CSV 내보내기** — 문서에 붙이지 않은 링크는 클릭해도 아무 일이 없는 브라우저가 있고, 곧바로 `revokeObjectURL` 하면 내려받기가 시작되기 전에 주소가 사라져 빈 파일이 된다. 붙였다 지우고, 정리는 미룬다
- **운동 종류로 걸렀을 때 화면이 통째로 비던 것** — 빈 날을 건너뛰기만 해서, 고른 운동이 한 번도 없으면 목록 자리가 아무것도 없이 남았다. 화면이 죽은 것처럼 보인다. `해당하는 기록 없음` 과 되돌리기 버튼을 넣었다
- **검색이 실패해도 지난 결과가 남아 있던 것** — 오류 문구 아래 옛 결과가 그대로 붙어 검색이 된 것처럼 읽혔다. 실패하면 목록을 비운다
- **검색 경쟁 상태** — 외부 DB 라 8초까지 기다린다. 두 번 치면 늦게 온 응답이 새 검색을 덮어썼다. 요청에 번호를 매겨 마지막 것만 반영한다. 글자 검색과 부위 버튼이 두 벌로 갈라져 있던 것도 한 길로 합쳤다
- **미니게임이 함수 하나 때문에 파칭코 화면(683줄)을 통째로 끌어오던 것** — `earnedTickets` 를 `data/pachinkoData` 에서 바로 가져온다 (8/21 에 제보 폼에서 겪은 것과 같다)
- **실패 알림이 성공 색으로 뜨던 것** — 측정 · 루틴 · 인바디 · 비교 화면에서 `toast(...)` 에 `'error'` 가 빠져 있었다. 저장에 실패했는데 초록색으로 뜬다

**설명에 쓰는 숫자를 손으로 적지 않는다**

FAQ 가 상수를 읽게 하려고 두 곳을 열었다. 밸런스를 바꾸면 설명이 저절로 따라온다.

- `LevelSystem` 에 `EXP_PER`(운동 15 · 인바디 30). `calcExp` 안에 박혀 있던 숫자다
- `plateData` 에 `BASE_DAILY_PLAYS`(5). **`PLATE_RULE.dailyPlays` 는 개발 빌드에서 9999 로 풀려 있어 설명에 쓸 수 없다** — 개발 화면에 「하루 9999판」이라고 뜬다
- 티켓 문답도 `원판 10개 = 티켓 1장` 을 `PLATE_RULE.perTicket` 에서 읽는다. 8/21 에 「미리 확인이 필요하다」고 적어둔 문장인데, 실제로 `plateData` 와 맞았다

## 제보 알림 — 화면을 열어봐야만 알던 것

제보가 들어와도 관리자가 화면을 열어보기 전에는 아무도 모른다. 며칠 안 들어가면 며칠 동안 답이 안 달린다. 욕설로 걸린 사람은 그동안 앱을 못 쓴 채 방치된다.

**두 갈래로 걸었다.** 하나는 설정이 필요하고, 하나는 지금 바로 된다.

**1) 메일 — 서버가 보낸다 (세션과 무관)**

`utils/mailer.js` 에 `notifyAdmin()` 을 뒀다. `ADMIN_EMAIL` 로 보낸다.

- **제보가 들어오면** — 유형 · 제목 · 화면 · 회원 번호까지만. 본문을 통째로 넣으면 메일함이 제보함이 된다
- **욕설 · 비하로 걸리면** — 판정 · 걸린 말 · 조치 · 원문 300자. 사전이 잘못 잡았을 때 되돌리라는 안내까지
- **메일이 안 나가도 앱은 아무 영향이 없다.** SMTP 가 없으면 조용히 건너뛰고, 실패해도 삼킨다. 기다리지도 않는다 — 알림 때문에 제보 접수가 실패하면 본말이 전도된다
- 제보는 **10분에 한 통**으로 묶는다. 몰리면 메일함이 터진다.
  **욕설은 묶지 않는다** — 사전이 잘못 잡았을 수 있고, 묶어서 늦게 보내면 그만큼 늦게 풀린다

**아직 안 나간다.** `SMTP_HOST` · `SMTP_USER` · `SMTP_PASS` 가 설정되어 있지 않다. 같은 이유로 **비밀번호 찾기 메일도 운영에서 안 나간다** — 이건 원래부터 그랬다.

**2) 관리자 화면 배지 — 설정 없이 바로 된다**

더보기 탭과 관리자 항목에 **손볼 건수가 빨간 숫자로 붙는다.** 안 끝난 제보 + 확인 안 한 욕설 기록.

- `GET /api/reports/pending` — 숫자 둘만 돌려준다. 표시 하나 때문에 제보를 통째로 받아올 수는 없다
- 3분마다, 그리고 **다른 탭에서 답을 달고 돌아오면 그 즉시** 다시 센다
- 관리자가 아니면 아예 부르지 않는다

**확인** — 제보 한 건 → `{open:1, abuse:0}` · 욕설 제보 → 차단되고 `{open:1, abuse:1}` · SMTP 없이도 서버 멀쩡.

## 화면이 없던 기능 두 개를 붙였다

서버는 있는데 **누를 곳이 없던** 것 둘. API 와 화면을 대조해서 찾았다.

**비밀번호 변경**

`PUT /api/auth/password` 는 처음부터 있었는데 화면이 어디에도 없었다. **로그인한 사람이 비밀번호를 바꿀 방법이 없었다.** 로그인 화면의 `비밀번호를 잊으셨나요?` 는 **찾기**(이메일 인증)라서 다른 것이다.

- 프로필 메뉴, 닉네임 바꾸는 그 자리에 붙였다
- 서버 규칙(8~100자 · 영문+숫자)을 화면에서 먼저 걸러 되돌아오는 시간을 아낀다. 두 번 적기와 「지금 쓰는 것과 같아요」도 본다
- **바꾸면 서버가 그 계정의 refresh token 을 전부 지운다** — 다른 기기에서도 로그아웃된다. 그게 맞는 동작이라 미리 말해주고, 성공하면 이쪽도 로그아웃하고 로그인으로 보낸다. 안 그러면 다음 요청에서 401 을 맞고 영문 모른 채 튕긴다

**계정 삭제 (관리자)**

자동 판정에서 계정 삭제를 없애면서 `DELETE /api/security/user/:id` 를 열었는데, **버튼을 안 만들었다.** 「없애는 것은 사람이 한다」고 해놓고 아무도 못 하는 상태였다.

- 보안 관리 탭의 회원 목록에 붙였다. **`blocked` 인 사람에게만 보인다** — 멀쩡한 사람 옆에 삭제 버튼이 늘 붙어 있으면 언젠가 눌린다
- 확인 창은 「정말요?」로 끝내지 않는다. **지울 계정의 이메일을 그대로 적어야** 버튼이 살아난다. 누구를 지우는지 눈으로 보고 손으로 옮겨 적게 하는 것이다
- 무엇이 사라지는지(운동 기록 · 인바디 · 측정 · 루틴 · 사진 · 제보) 그대로 적어둔다

**확인** — 임시 계정을 만들어 한 바퀴 돌렸다.
현재 비번 틀림 401 · 새 비번 규칙 위반 400 · 변경 200 · 옛 비번 로그인 401 · 새 비번 로그인 200 ·
차단 전 삭제 400 · 차단 200 · 이메일 틀림 400 · 이메일 맞음 200 · 삭제 뒤 로그인 401, DB 에 흔적 없음.

## 개발 서버가 DB 를 쓸 때마다 재시작하고 있었다

위 확인을 돌리다 찾았다. `block-user` 가 **「차단되었어요」 라고 답해놓고 실제로는 안 바뀌었다.**

- `backend/ironlog.json` 은 DB 파일인데 `backend/` 안에 있고 확장자가 `.json` 이다. nodemon 은 기본으로 `js,mjs,cjs,json` 을 감시한다 — **기록 하나 저장할 때마다 서버가 재시작했다**
- `db.js` 는 500ms 지연 저장이다. 그 사이에 재시작이 걸리면 **방금 쓴 것이 통째로 사라진다**
- `nodemon.json` 을 두어 `src` 만 보고 DB 파일과 로그는 무시하게 했다. 고친 뒤 차단·삭제가 그대로 남는다

운영에는 영향이 없다(`npm start` 는 nodemon 을 안 쓴다). 다만 **개발 중 확인 결과를 믿을 수 없게 만드는 종류의 문제**라 오래 두면 위험하다.

## 두 번째 훑기 — 놓쳤던 것

**점검 기능이 아무 일도 하지 않고 있었다**

가장 큰 것. 점검 스케줄이 **관리자 브라우저의 localStorage 에만** 있었다. 백엔드에는 관련 코드가 한 줄도 없다.

- 관리자가 점검을 잡아도 **다른 사람에게는 아무 일도 일어나지 않는다.** 점검 화면도 안 뜨고, 고객센터의 `점검 예정` 도 영영 비어 있다
- 관리자가 브라우저를 바꾸거나 캐시를 지우면 자기 설정도 사라진다
- **기능이 있는 것처럼 보였을 뿐이다.** 8/21 에 「날짜·시간 예약」과 「자정 넘김」을 고쳐뒀는데, 그 아래가 비어 있었다

서버로 올렸다. `GET /api/maintenance`(누구나) · `PUT /api/maintenance`(관리자).

- 화면은 **캐시로 먼저 그리고 서버에서 받아 갱신한다.** 목록을 못 받은 것 때문에 앱이 안 열리면 안 된다
- 열자마자 한 번, 그 뒤로는 5분마다 받는다. 시각 계산은 그대로 1초마다 — 목록을 1초마다 부르면 서버가 상한다
- 서버가 모양을 검사한다. 모르는 키는 버리고, **하루를 넘는 점검은 안 받는다** — 넘기면 화면이 영원히 잠긴다
- 관리자 화면은 저장에 실패하면 되돌린다. 저장한 줄 알았는데 다른 사람에게 안 걸려 있는 게 제일 나쁘다
- 확인: 일반 계정 저장 403 · 관리자 저장 200(모르는 키는 버려짐) · `durationMin: 99999` 는 기본값으로 떨어짐 · 목록이 아니면 400

**오프라인에서 앱이 아예 안 열렸다**

서비스 워커가 네트워크 실패 시 `caches.match(요청)` 을 그대로 돌려줬다.

- 이 앱은 한 페이지짜리라 `/support` · `/history` 같은 주소에 해당하는 파일이 **따로 없다.** 캐시에 없으니 `undefined` 가 나가고, `respondWith(undefined)` 는 그 요청을 그냥 깨뜨린다 — **홈 화면에 추가해둔 앱을 비행기 모드에서 열면 안 떴다**
- 주소로 들어온 화면(`navigate`)이면 `/index.html` 로 돌린다. 라우팅은 앱이 알아서 한다
- 돌려줄 것이 없으면 `Response.error()` — 「네트워크 실패」를 분명히 알린다
- **남의 집 응답을 캐시하던 것도 막았다.** 운동 검색(wger.de)이나 날씨 응답까지 담아두면 캐시가 계속 부풀고 옛 결과가 되살아난다. 이제 우리 집(`type === 'basic'`) 것만 담는다

**물음 창이 겹치면 기다리던 쪽이 영영 멈췄다**

`confirmDialog()` 는 promise 를 돌려준다. 그런데 이미 열려 있는데 또 부르면 `setState(next)` 가 앞의 것을 **덮어썼다.** 앞의 물음은 화면에서 사라지고 그 promise 는 영영 안 풀린다 — 그것을 `await` 하던 코드가 그 자리에서 멈춘다. 덮어쓰지 않고 줄을 세운다.

**그 밖에**

- `MaintenanceScreen` 도 import 가 파일 한가운데 있었다. 위로 올렸다
- `saveSchedules`(로컬 전용 저장)는 이제 쓰는 곳이 없어 지웠다 — 남겨두면 서버를 건너뛰고 저장하는 길이 된다

훑었지만 손대지 않은 곳 — 원판 피하기 · 파칭코 티켓 계산 · 욕설 누적(`countAbuse` 는 짜증과 되돌린 것을 이미 제외한다) · 측정 저장 검증 · `safeStorage`. 모두 이미 단단하다.

## 정리 · 두 번째 최적화

**목록 카드가 매번 다시 그려지고 있었다**

히스토리 · 운동 기록 · 인바디는 카드를 몇 백 개씩 늘어놓는다. 부모가 한 번 다시 그려지면 카드가 전부 따라 그려졌다.

- `WorkoutCard` · `InbodyCard` 를 `memo` 로 감쌌다
- 그것만으로는 안 걸린다 — **부모가 넘기는 `onDelete` · `onEdit` 이 매 렌더 새로 만들어지면 memo 는 아무 일도 못 한다.** 세 화면의 핸들러를 `useCallback` 으로 고정했다

**차트 덩어리를 직접 묶던 것을 놓아줬다**

`manualChunks` 에 `charts: ['recharts']` 가 있었다. 한 덩어리로 묶으면 **선 그래프만 있는 화면에서도 레이더 차트 코드까지 같이 받는다.** 빼두니 롤업이 화면별로 나눠준다 — 비교 탭의 레이더(14.4KB)는 이제 비교 탭에서만 받는다.

큰 이득은 아니다. 그래프 라이브러리의 몸통(367KB)은 여전히 공유다. 정직하게 적자면, 여기서 더 줄이려면 그래프를 직접 SVG 로 그려야 한다 — 인바디 화면 전체를 다시 그리는 일이라 지금은 안 했다.

**손으로 또 적던 것 · 아무도 안 쓰던 것**

- `WorkoutPage` 가 오늘 날짜를 손으로 만들고 있었다. **8/21 에 새벽 기록이 사라지던 버그가 나온 자리가 바로 이 식이다.** 공용 `dateKey()` 로 바꿨다
- `Layout` 의 `MenuItem` — 정의만 있고 아무도 안 쓴다. 지웠다
- `introData` 의 `TICKET_ROWS` — 지운 시안들이 쓰던 것이다. 같이 지웠다
- `Badges` 의 import 세 줄이 파일 한가운데 있었다. 위로 올렸다
- 서비스 워커 등록 로그가 운영 콘솔에도 찍혔다. 개발 빌드에서만 찍는다

**지울 길을 안 만들고 지우는 것만 막아뒀다**

자동 판정에서 `deleteUserCompletely` 를 뺐는데, **사람이 지울 경로를 안 만들었다.** 「없애는 것은 사람이 한다」고 해놓고 아무도 못 하게 된 상태였다. `DELETE /api/security/user/:id` 를 열었다.

- 관리자는 못 지운다
- **이미 막혀 있는 사람만** 지울 수 있다 (영구 정지 · is_banned · 차단). 목록에서 잘못 눌러 멀쩡한 사람이 사라지면 안 된다
- **지울 계정의 이메일을 본문에 그대로 적어야 한다.** 누구를 지우는지 보고 누르게
- 확인: 멀쩡한 사용자 → 400, 관리자 → 400, 없는 사용자 → 404. 세 경우 모두 아무것도 지워지지 않았다

## 위험한 것부터 찾아 고쳤다

### 1. 아무나 배포한 사이트가 이 API 를 부를 수 있었다

CORS 허용 목록에 **`*.onrender.com` 이 통째로** 들어 있었다. `credentials: true` 와 함께.

- Render 는 누구나 무료로 배포할 수 있는 곳이다. `evil-xxx.onrender.com` 을 띄우고 그 페이지에서 `credentials` 를 실어 이 API 를 부르면, **로그인해 있는 사람이 그 페이지를 열기만 해도** 그 사람 자격으로 요청이 나가고 응답까지 읽힌다
- `FRONTEND_URL` 에 이미 `https://steel-body.onrender.com` 이 정확히 들어 있다. 와일드카드는 애초에 필요 없었다. Render 가 넣어주는 `RENDER_EXTERNAL_URL` 도 같이 받아 배포 이름이 바뀌어도 끊기지 않게 했다
- OAuth 의 돌아갈 곳 판정(`isAllowedFrontendOrigin`)과 호스트 검증에도 같은 와일드카드가 있었다 — 열린 리다이렉트다. 같이 좁혔다
- 확인: 허용된 origin 은 200, `https://evil-test.onrender.com` 은 403 이고 `Access-Control-Allow-Origin` 헤더가 아예 안 붙는다

### 2. Bearer 헤더 하나로 CSRF 검사를 건너뛸 수 있었다

`if (req.headers.authorization?.startsWith('Bearer ')) return next();`

Bearer 만 쓰는 요청은 CSRF 가 필요 없다는 건 맞다. 그런데 **헤더가 있으면 통과** 로 둔 게 문제였다. `auth` 미들웨어는 쿠키를 먼저 읽는다 — 아무 값이나 담은 Bearer 헤더를 붙이면 **CSRF 검사만 건너뛰고 인증은 쿠키로 통과한다.** 1번과 겹치면 그대로 뚫린다. 쿠키가 없을 때만 건너뛰게 고쳤다.

### 3. 정상적으로 운동을 적으면 7일 정지됐다

스팸 기준이 **10건/분** 이었다. 그런데 **운동은 기록 하나가 POST 하나다** — 운동을 끝내고 앉아서 몰아 적으면 5개 종목 × 3세트만 해도 15건이다.

- 걸리면 7일 정지, 그리고 **두 번 걸리면 계정이 지워졌다** (`executeLevel3` → 누적 2회 → `executeLevel4`)
- 기준을 60건/분으로 올리고, **정지 대신 429 로 되돌려 보낸다.** 너무 빠른 것과 나쁜 뜻으로 하는 것은 다르고, 이 판정만으로 사람을 일주일 막아 세우기에는 근거가 약하다. 진짜 공격은 IP 차단과 rate limit 이 잡는다

### 4. 자동 판정이 계정과 모든 데이터를 지웠다

`executeLevel4` 가 `deleteUserCompletely` 를 불렀다. 몇 년치 운동 기록이 **되돌릴 방법 없이** 사라진다. 8/21 에 욕설 경로에서 이 함수를 일부러 떼어낸 것과 같은 이유가 여기에도 그대로 있었다.

- 막는 것(영구 정지 + 로그인 차단 + 이메일·IP 블랙리스트)은 자동으로 하되, **없애는 것은 사람이 한다.** 관리자가 화면에서 확인하고 직접 지운다
- **IP 대역(/24) 자동 차단도 뺐다.** 통신사 NAT 뒤에 있는 사람들이 통째로 걸린다. 대역이 필요하면 관리자가 보고 직접 넣는다
- `모든 데이터가 삭제되었습니다` 라고 적혀 있던 안내문도 사실에 맞게 고쳤다

### 5. 관리자가 자동 처벌에 걸렸다

`auth` 미들웨어는 관리자를 정지 검사에서 빼주는데, **처벌을 거는 쪽(`executeLevel3` · `executeLevel4`)은 관리자를 보지 않았다.** 관리자에게 걸리면 자기 정지를 자기가 못 풀어 서비스가 통째로 멎는다. 두 함수 모두 관리자면 기록만 남기고 건너뛴다.

### 6. `unblock` 이 관리자 권한을 지웠다

`POST /api/security/unblock-user/:id` 가 대상이 누구든 역할을 `'user'` 로 덮어썼다. 관리자에게 실수로 누르면 그 자리에서 권한이 사라진다 — `revoke-admin` 에는 자기 자신을 지키는 장치가 있는데 이쪽으로는 그냥 통과했다.

- 차단된 사람(`role === 'blocked'`)만 풀도록 막았다
- **마지막 관리자는 강등할 수 없게** 했다. 자기 자신만 막아두면 관리자 둘이 서로를 내리는 길이 남는다

### 7. 대문자로 가입하면 계정이 둘로 갈렸다

이메일을 그대로 비교하고 있었다.

- `Kevin@Gmail.com` 으로 가입한 사람이 `kevin@gmail.com` 으로 로그인하면 **「없는 계정」** 이 되고, 게다가 그 주소로 **또 가입이 된다.** 같은 사람의 계정이 둘로 갈리고 기록도 갈린다 — 본인에게는 「기록이 사라졌다」로 보인다
- 저장은 적은 그대로 두고, 찾고 비교할 때만 낮춘다(`emailKey`). 인덱스 · 중복 검사 · `ADMIN_EMAIL` 판정 전부
- 확인: `DEV3@Local.DEV` 로 로그인하면 `dev3@local.dev` 와 같은 계정(userId 7)이 나온다

### 8. 사진 자리에 사진이 아닌 것을 넣을 수 있었다

`POST /api/photos` 가 아무 문자열이나 2MB 까지 받아 그대로 돌려줬다. `data:image/...;base64,` 로 시작하는 것만 받게 했다.

**아직 안 고친 것** — refresh token 이 평문으로 저장된다. 해시해서 넣는 게 맞지만, 바꾸면 지금 로그인해 있는 사람이 전부 로그아웃된다. 배포 시점을 골라야 해서 남겨뒀다.

## 제보를 쓰기 전에 한 번 묻는다

유형(버그 · 문의 · 건의)을 고르기 전 자리에는 `고르시면 그에 맞춰 물어봅니다` 라는 안내만 있었다. 그 자리에서 먼저 묻는다 — **`무엇이 궁금하세요?`**

답이 이미 있는 질문을 제보로 받으면 물어본 사람은 며칠을 기다리고, 답하는 쪽은 같은 답을 또 쓴다. 여기서 끝나면 둘 다 안 한다.

- 치는 대로 자주 묻는 것에서 찾아 보여준다. 누르면 답이 그 자리에서 펼쳐진다
- 아무것도 안 쳤으면 `자주 묻는 것 7가지 펼쳐보기` 만 놓아둔다. 목록을 먼저 들이밀면 제보하러 온 사람이 벽을 만난다
- **막지 않는다.** 「찾는 게 없다」를 눌러야 폼이 열리는 식으로 만들지 않았다 — 그런 관문은 사람을 돌려보내는 데만 쓰인다. 답이 없으면 그대로 유형을 골라 적으면 된다
- 답이 없을 때는 그렇게 말한다 — `여기에는 답이 없네요. 위에서 유형을 고르고 적어주시면 확인하고 답을 답니다`

**제목을 치는 동안에도 찾는다**

유형을 고르고 제목을 적는 사이에도 `혹시 이걸 찾으시나요?` 로 최대 두 개를 띄운다. 세 개가 넘으면 폼 위에 답이 쌓여 무엇을 적으러 왔는지가 가려진다.

**찾는 방식**

- 공백과 기호를 지우고 맞춘다 — `초 월` 도 `초월` 로 친다
- **두 글자부터** 찾는다. 한 글자로 찾으면 거의 모든 항목이 걸려서 도움이 안 되고, 치는 동안 목록이 요동친다
- 점수는 어디서 맞았는지로 매긴다 — 질문(3) > 키워드(2) > 답 본문(1)
- 키워드는 **사람들이 실제로 칠 법한 말**을 넣었다. 화면에 적힌 단어와 물어볼 때 쓰는 단어는 다르다 — `정지` 를 `차단` · `막혔` 으로 친다
- 실제 검색어로 돌려 확인했다: `렙업` · `경험치` → 레벨, `폰바꿈` · `기록이 사라졌어요` → 기록 보관, `차단당했어요` → 정지. **`벤치프레스가 안 눌려요` 같은 진짜 버그 제목에는 아무것도 안 뜬다** — 엉뚱한 제안이 뜨면 그게 더 방해다

**말투와 모양을 다시 잡았다**

처음 만든 화면은 **사무적이고 쫓아내는 말로 읽혔다.** 지적을 받고 고쳤다.

- `무엇이 궁금하세요?` 라는 제목과 빈 칸만 덩그러니 있었다 → `💬 먼저 하나만 여쭐게요` + 「궁금해서 오신 거라면 여기서 바로 답을 드릴 수 있어요. 기다리지 않으셔도 되니까요」
- **무엇을 쳐야 할지 모르는 사람이 대부분인데 빈 칸만 들이밀었다.** 주제를 눌러 바로 볼 수 있게 칩을 뒀다 — `티켓` · `초월 · 개벽` · `확률표` · `레벨` · `미니게임` · `기록 보관` · `정지`. 누르면 그 자리에서 답까지 펼쳐진다 (한 번 더 누르게 하지 않는다)
- `여기서 못 찾으셨으면 위에서 유형을 골라주세요` → 「찾으시는 게 없어도 괜찮습니다. 위에서 유형만 골라주시면 **나머지는 제가 여쭤볼게요**」
- `버그는 재현할 정보를 … 받습니다` — 관공서 말투였다 → 「버그는 **어떻게 하면 그렇게 되는지**, 문의는 **궁금하신 것만**, 건의는 **어떤 게 아쉬우셨는지** 여쭙습니다」
- `여기에는 답이 없네요` → 「여기에는 딱 맞는 답이 없네요. **그 이야기는 제가 직접 듣는 게 낫겠습니다** — 위에서 유형만 골라주세요」
- 벽에 붙은 글자 같던 것을 옅은 상자에 담고 왼쪽에 강조선을 뒀다. 바깥 안내문은 상자 밖으로 빼서 위계를 갈랐다

FAQ 목록은 `pages/support/faq.js` 로 옮겼다. 고객센터의 `자주 묻는 것` 과 제보함이 같은 목록을 본다 — 두 곳이 어긋날 수 없다.

## 만족도 — 아무 말 없는 사람의 온도를 받는다

제보함은 **할 말이 있는 사람만** 쓴다. 그런데 대부분은 할 말까지는 없고 그냥 쓰고 있을 뿐이다 — 그 사람들의 온도는 제보함으로는 영영 안 온다. 누르는 데 1초면 되는 것을 따로 하나 뒀다.

- 고객센터 히어로 바로 아래, 한 줄짜리 별점(`이 앱, 쓰시기 어떠세요?`)
- **이유는 묻지 않는다.** 여기서까지 물으면 누르는 게 일이 되고, 제보함과 같은 것을 두 곳에서 묻게 된다. 대신 **2점 이하를 주면 그 자리에서 제보함을 열어준다** — 「무엇이 아쉬웠는지 한 줄만 적어주시면 그걸 고칩니다」
- **한 사람당 한 줄만 남는다.** 여러 줄을 쌓으면 자주 누른 사람이 평균을 끌고 간다. 다시 매기면 덮어쓴다
- 한 번 매기면 다음부터 이 줄이 아예 안 나온다. 다만 **매긴 직후에는 `다시 매기기` 가 있다** — 별 하나를 잘못 눌러놓고 고칠 길이 없으면 안 된다
- 매긴 기록은 서버가 들고 있다. 화면에만 두면 기기를 바꿀 때마다 다시 묻는다
- 못 불러오면 이 줄은 조용히 접힌다. 별점을 못 물어본 것은 아무것도 망가뜨리지 않는다

**관리자는 분포만 본다**

`제보 관리` 탭 맨 위, 욕설 기록 아래에 붙는다. **누가 몇 점을 줬는지는 서버가 아예 돌려주지 않는다** — 점수를 보고 사람을 대하기 시작하면 솔직한 점수가 안 들어온다.

- 평균 하나만 크게 띄우지 않는다. `4.2` 라는 숫자보다 **1점이 몇 명인가** 가 할 일을 정한다. 별 5개부터 1개까지 막대로 늘어놓고, 2점 이하가 있으면 그 수를 따로 빨갛게 적는다

`POST /api/ratings` · `GET /api/ratings/me` · `GET /api/ratings/stats`(관리자). 확인 — 처음엔 `null`, 매기면 저장, 다시 매기면 덮어쓰기, 1~5 밖의 값은 400, 일반 계정이 통계를 부르면 403.

## 움직임과 무게 — 최적화

**누르면 반응한다**

모바일에는 hover 가 없다. 그런데 버튼·카드·탭에 `:hover` 만 걸려 있어서 **손가락으로 눌러도 화면이 그대로였다.** 먹었는지 알 수 없으니 같은 자리를 두 번 누르게 된다.

- 눌린 동안 `scale(0.985)` 로 살짝 들어가게 했다. 0.08초라 눈에 거슬리지 않고 손끝에는 잡힌다
- `-webkit-tap-highlight-color: transparent` — 누를 때 파랗게 번쩍이던 사각형을 없앴다
- `touch-action: manipulation` — 브라우저가 더블탭 확대를 기다리느라 넣던 **300ms 지연**이 사라진다. 버튼이 즉시 눌린다
- `transition: all` 을 쓰던 곳(버튼·탭·카드)을 실제로 변하는 속성만 적게 바꿨다. `all` 은 레이아웃 속성까지 대상으로 잡아 매 프레임 계산이 붙는다
- OS 에서 `동작 줄이기` 를 켠 사람에게는 애니메이션을 걷어낸다 (`prefers-reduced-motion`)

**화면을 옮기면 맨 위에서 시작한다**

스크롤 위치를 되돌리는 곳이 아무 데도 없었다. 히스토리를 한참 내려보다 루틴으로 넘어가면 **루틴 화면이 한가운데부터 보였다.**

- 새 화면으로 갈 때만 맨 위로 올린다. 뒤로 가기(POP)는 그대로 둔다 — 보던 자리로 돌아가는 게 맞다
- 등장 애니메이션도 고쳤다. `pageIn` 이 `.content-area` 에 걸려 있었는데 그 껍데기는 라우트가 바뀌어도 남아 있어서, **앱을 처음 열 때 한 번 돌고 그 뒤로는 아무 일도 없었다.** 주소를 key 로 준 안쪽 껍데기로 옮겨 화면마다 짧게 떠오른다

**무거운 그래프를 나중에 받는다**

`recharts` 는 이 앱에서 제일 무거운 덩어리다 — **415KB (gzip 110KB).** 인바디와 히스토리가 위에서 그냥 `import` 하고 있어서, 그 화면에 들어가면 입력 폼도 기록 목록도 그 덩어리를 다 받을 때까지 안 그려졌다.

- 그래프를 따로 떼어 `lazy` 로 받는다. 화면을 먼저 띄우고 그래프만 뒤늦게 채운다
- 자리는 미리 잡아둔다 — 안 그러면 도착하는 순간 아래 내용이 밀려 내려간다
- 인바디의 `비교` 탭도 눌렀을 때 받는다
- 인바디 화면 번들 **31.8KB → 19.7KB**, 히스토리는 415KB 를 진입 경로에서 통째로 뺐다
- 기록이 두 개도 안 되면 그래프를 그릴 일이 없으므로 덩어리도 받지 않는다

**긴 목록은 보이는 것만 그린다**

운동 카드와 인바디 카드에 `content-visibility: auto` 를 붙였다. 화면 밖 카드는 그리기를 건너뛴다 — 기록이 몇 백 개 쌓이면 스크롤이 끊기던 자리다. 대략의 높이를 같이 일러줘 스크롤바가 튀지 않게 했다.

**첫 글자가 늦게 뜨던 것**

폰트를 `globals.css` 안의 `@import` 로 부르고 있었다. 브라우저가 CSS 를 받아 파싱한 **뒤에야** 폰트 CSS 를 요청한다 — 요청이 한 단계 더 붙는다. `index.html` 의 `<link>` 로 옮겼다. 브라우저 위쪽 띠 색(`theme-color`)도 앱 배경과 맞췄다 (빨강이 남아 있었다).

**그 밖에**

- `useIsPC` 가 `Layout` 과 `TabBar` 에 각각 있었다. resize 리스너가 둘, 대기 시간도 서로 달라(150ms / 100ms) **창을 줄이면 사이드바와 탭바가 한 박자 어긋나게** 바뀌었다. 하나로 합쳤다
- `feed.jsx` 가 목록 데이터와 컴포넌트를 같이 내보내 개발 중 Fast Refresh 가 매번 포기하고 화면을 통째로 새로 그렸다. `feedData.js` 와 `FeedList.jsx` 로 나눴다
- 홈의 `getWeekDates()` 가 매 렌더 새 배열을 만들어 그 아래 `useMemo` 가 무의미했다

**욕설 · 비하를 걸러내고 되풀이하면 수위를 올린다**

제보함은 화가 난 사람이 오는 곳이다. 그래서 두 가지를 갈랐다 — **화풀이**와 **남을 해치려는 말**은 다르게 다룬다.

`sanitize()` 는 연속 공백을 하나로 누른다. 줄바꿈도 공백이라 같이 눌린다.

- 확인: `<script>` 는 그대로 걸러지고 줄바꿈만 남는다

**관리자 화면에 `제보 관리` 탭**

지운 `공지사항 관리` 자리다. 탭 순서는 맨 앞에 뒀다 — 사람이 기다리고 있는 목록이다.

- 기본 화면은 **`안 끝난 것`**(접수 + 확인중). 전체 목록을 먼저 보여주면 이미 끝낸 것부터 읽게 된다
- 한 줄에서 유형 · 상태 · 답변 여부 · 회원 번호 · 날짜를 본다. 버그면 화면 이름과 빈도가 꼬리표로 붙는다
- 펼치면 본문 · 기기 정보 · 상태 버튼 넷 · 답변 칸. 답변은 고치고 지울 수 있다
- **기본 탭은 `점검 스케줄` 로 뒀다.** 제보함이 아직 앱에 안 붙어 있어 제보가 들어올 수 없다 — 지금 기본으로 두면 관리자 화면이 빈 목록으로 열린다 (8/20 에 같은 이유로 고쳤던 자리다). 붙이는 날 바꾼다

**못 불러온 것과 없는 것을 구분한다**

- 목록을 못 가져왔을 때 빈 화면을 띄우면 **보낸 제보가 지워진 줄 안다.** `없어진 게 아니라 못 가져온 것` 이라고 말한다
- 보내기 실패도 삼키지 않는다. 성공 문구보다 먼저 보이게 뒀다
- 지우기는 화면에서 먼저 지우고 서버에 알린다. 실패하면 되돌린다 — 지운 줄 알았는데 새로고침하면 살아 있는 것이 제일 나쁘다
- id 와 날짜는 서버가 정한다. 화면에서 미리 만들어 붙였다가 실패하면 목록에 유령이 남는다

**확인** — 등록 · 목록 · 삭제 · 관리자 전체 조회 · 상태 변경 · 답변 달기를 실제 서버로 한 바퀴 돌렸다. 유형 없이 · 제목 없이 보내면 막히고, 일반 계정으로 관리자 경로를 부르면 403 이다. 남의 제보는 안 지워지고, 관리자가 제목을 같이 보내도 무시된다. 여러 줄 본문과 답변이 그대로 돌아온다.

**새벽에 남긴 기록이 홈에서 사라지던 것**

날짜 키를 만드는 방법이 저장하는 쪽과 읽는 쪽에서 서로 달랐다.

- 저장 — `WorkoutPage` 는 **로컬 날짜**로 키를 만든다 (`getFullYear/getMonth/getDate`)

- `data/dateKey.js` 하나를 두고 `HomePage`(2곳) · `MissionSystem` · `preview/introData.js`(2곳) · `preview/ReportPreview.jsx` 가 그것만 쓰게 했다
- 확인: 운영 빌드 통과. 시안 문자열은 여전히 `dist` 에 0건

**같은 종류를 전부 훑었다**

한 곳만 고치면 나머지가 언젠가 같은 버그가 된다. `toISOString()` 으로 날짜 키를 만들던 곳을 전부 없앴다.

- 홈 밖에도 같은 게 있었다 — `InbodyPage`(기록 폼 기본 날짜) · `MeasurePage`(측정 저장 날짜) · `ShoulderSection` · `MaintAdmin`(점검 예약 기본 날짜). 새벽에 열면 어제 날짜가 미리 채워져 있었다
- **같은 헬퍼가 세 군데에 따로 있었다.** `Badges.toLocalDate` 와 `plateData.todayKey` 는 이미 로컬 기준이라 안 틀렸지만, 셋이 따로 있으면 넷째가 또 생긴다. `data/dateKey.js` 하나로 합치고 부르던 이름은 그대로 뒀다
- 이제 `src` 전체에 날짜 키를 만드는 `toISOString()` 이 없다

**공지함 라벨이 커밋 종류를 그대로 쓰던 것**

`공지사항 기능 제거` 가 화면에 **새 기능**으로 떴다. `라이트 테마 제거` 도 마찬가지였다.

- 커밋 종류(`feat`)는 무엇을 한 코드인지를 말할 뿐이다. 읽는 사람이 알고 싶은 건 **없어졌는지 달라졌는지**다
- `feat` 일 때만 제목을 보고 `제거` · `바뀜` 으로 가른다. 애매하면 `새 기능` 을 그대로 둔다 — 틀린 라벨보다 밋밋한 라벨이 낫다
- 확인: `공지사항 기능 제거` → **제거**, `최근 바뀐 것을 기능 소개 위로` → **바뀜**, `라이트 테마 제거` → **제거**, `fix`·`perf` 는 그대로

**공지함이 최근 8건만 들고 있던 것**

`전부 보기` 라고 해놓고 `gen-changelog.mjs` 가 커밋 8건만 담았다. 오늘 커밋 일곱 개를 올리니 **어제·그제 것이 통째로 밀려났다.** 공지함은 지난 것을 되짚는 자리인데 그게 안 된다. 40건으로 올린다. 홈페이지가 여섯 줄만 보여주는 건 그대로다 — 몇 개를 보여줄지는 화면이 정한다.

**한 줄이 모자라서 목록 전체가 죽던 것**

`feed.jsx` 가 `c.date.slice(5)` 를 무방비로 불렀다. `notices.json` 은 내가 손으로 적는 파일이라 `date` 를 빠뜨릴 수 있는데, 그러면 그 줄만 이상해지는 게 아니라 홈 화면이 통째로 흰 화면이 된다. 날짜와 키 둘 다 없을 때를 받아준다.

**제보 목록에 정렬이 없던 것**

예시 세 건은 날짜 오름차순인데 새 제보는 맨 위에 붙어서, 하나만 보내도 순서가 섞였다. 날짜 역순(같은 날이면 나중 것)으로 세운다. 서버에 붙이면 서버가 할 일이지만, 그때까지 이상하게 보일 이유가 없다.

**점검 예약이 날짜와 시간을 통째로 무시하던 것**

관리자 화면의 `점검 스케줄` 탭에는 **날짜 · 시작 시간 · 소요(분)** 칸이 있고, 그 옆에 요약 줄이 뜬다 — `2026년 8월 25일 화요일 03:00 ~ 04:00 (60분간)`. 그런데 버튼이 부르던 `startNow()` 는 **그 값을 하나도 안 봤다.** `now.getHours()` 로 지금 시각을 찍어 넣었다.

- 다음 주 점검을 잡으려고 날짜를 고르고 버튼을 누르면 **그 자리에서 사이트가 닫힌다.** 접속 중인 사람 전부에게 점검 화면이 뜬다
- 화면의 요약 줄은 입력한 값을 그대로 보여주므로 무엇이 잘못됐는지도 안 보인다
- 정기 · 서버 · 긴급 세 블록이 전부 같은 함수를 불렀다
- `scheduleMaint(type, 날짜, 시간, 분, 사유)` 로 바꿨다. 기본값이 오늘·지금이라 그냥 누르면 예전처럼 즉시 시작한다. 버튼 글자도 실제 동작을 따라간다 — 지금이면 `시작`, 나중이면 `예약`
- 이미 끝난 시각으로 잡으면 저장하지 않고 `이미 지난 시각이에요` 로 막는다. 걸린 줄 알고 기다리게 두지 않는다

**5분짜리 긴급 점검이 매일 되살아나던 것**

같은 `startNow()` 가 만든 항목은 `days: []` 였다. 점검 판정은 `days` 가 비면 **매일**로 읽는다.

- 긴급 점검 5분을 한 번 걸면, **다음 날도 그 다음 날도 같은 시각에 5분씩 사이트가 닫혔다.** 영원히
- 이제 즉시·예약 점검은 `date` 를 함께 저장한다. 그 하루만 돈다
- 이미 저장돼 있는 옛 항목(`type` 은 있는데 `date` 가 없는 것)은 **돌리지 않는다.** 목록에는 남아서 관리자가 지울 수 있다
- 목록도 구분해 보여준다 — 일회성은 `2026-08-25 하루`, 반복은 `매주 월, 화`

**자정을 넘는 점검이 저 혼자 풀리던 것**

`23:30` 에 60분을 걸면 종료가 분으로 `1470` 이다. 자정이 지나면 현재 시각은 `15`(00:15) 라 `nowMin >= 1470` 도 `nowMin >= 1410` 도 아니다.

- **자정에 점검이 저절로 끝나서 사이트가 열렸다.** 정작 점검은 진행 중이다
- 종료 시각 표시도 `24:30` 으로 떴다 (`% 24` 를 안 했다). 관리자 목록의 `endHour()` 도 같았다
- 오늘 시작한 창과 어제 시작해 넘어온 창을 둘 다 본다. 확인: `23:29` 평상 → `23:40` 점검중(종료 00:30) → `00:15` 점검중 → `00:31` 평상

**운동 기록을 수정하다 취소하면 날짜가 안 돌아오던 것**

2주 전 기록의 `수정` 을 누르면 폼 날짜가 그 날로 간다. 그런데 `수정 취소` 는 운동명 · 무게 · 세트 · 횟수를 전부 되돌리면서 **날짜만 안 되돌렸다.**

- 그 상태로 오늘 운동을 적으면 **2주 전 날짜에 저장된다.** 저장은 성공하고 토스트도 뜨는데 오늘 목록에는 안 보인다
- 수정을 마쳤을 때도 같았다. 폼은 `추가` 모드로 돌아가는데 날짜만 옛 기록에 남아 있었다
- `InbodyPage` 는 두 자리 모두 `setDate(today)` 를 이미 하고 있었다. 같은 화면 둘이 다르게 동작하고 있었던 것이다

**사진 한도가 프론트와 서버에서 서로 달랐던 것**

`base64` 는 원본보다 약 33% 커진다. 그런데 프론트는 **파일 크기**를 재고 서버는 **base64 길이**를 잰다.

- 프로필 사진 — 프론트 `2MB` 통과 → 서버 `base64 2MB` 초과로 거절. **1.5MB 를 넘는 사진은 전부 실패했다.** 사용자는 2MB 이하 사진을 골랐는데 `사진이 너무 커요 (최대 2MB)` 를 듣는다
- 비포/애프터 사진 — 프론트가 `5MB` 까지 받았다. `express.json` 한도가 `3mb` 라 큰 사진은 413 으로 튕겼다
- `data/photoLimit.js` 하나에 한도를 두고 둘 다 그것만 본다. 파일 크기와 인코딩 뒤 길이를 **둘 다** 검사한다. 서버 한도(base64 2MB)는 안 올렸다 — JSON 파일 DB 를 통째로 메모리에 올리는 구조라 사진이 커지면 그대로 힙에 눌러앉는다

**비포/애프터 사진이 서버 저장에 실패해도 `사진 저장!` 이라고 뜨던 것**

```js
client.post('/photos', ...).catch(() => {});   // 실패를 삼킨다
toast('사진 저장!');                            // 그리고 무조건 성공이라고 한다
```

- 사진은 `localStorage` 에도 저장되므로 **그 기기에서는 멀쩡히 보인다.** 기기를 바꾸거나 브라우저 데이터를 지우면 그때 사라진다
- 위의 한도 문제 때문에 1.5MB 넘는 사진은 **항상** 이 경로를 탔다. 저장된 줄 알고 원본을 지운 사람은 사진을 잃는다
- 성공하면 `사진 저장!`, 실패하면 `이 기기에만 저장됐어요 — 서버 저장에 실패했습니다`. 어디에 저장됐는지를 그대로 말한다
- 시안 FAQ 의 `기기를 바꿔도 같은 계정으로 로그인하면 그대로 있습니다` 가 사진에는 거짓말이었다. 이제 참이다

**무게 칸만 아무 검사도 없던 것**

`POST/PUT /workouts` 에서 운동명은 100자 제한에 새니타이즈까지 하는데, **바로 옆 무게는 body 값을 그대로 저장했다.**

- 무게는 `type="number"` 가 아니라 **자유 입력 칸**이다 (`60` · `20kg` · `맨몸` · `밴드` 를 다 받아야 해서)
- API 로 객체나 배열을 보내면 그대로 저장되고, 목록을 그리는 React 가 통째로 죽는다
- 길이 제한이 없어 아주 긴 문자열이 그대로 DB 에 눌러앉는다
- 문자열/숫자만 받고, 새니타이즈 후 30자로 자른다. 비면 `맨몸`

**CSV 내보내기에서 무게에 쉼표를 쓰면 열이 밀리던 것**

`export.js` 가 운동명만 따옴표로 감싸고 무게는 맨몸으로 뒀다.

- 드롭세트를 `20, 30, 40` 으로 적는 건 이상한 입력이 아니다. 그 줄부터 **세트·횟수 열이 통째로 밀린다**
- 무게도 감싼다. 숫자 칸(세트·횟수)은 감싸지 않는다 — 감싸면 엑셀이 글자로 읽어 합계가 안 된다

**히어로 문구를 다시 썼다**

```
전 : 오늘 든 무게를 적으면 / 그게 경험치가 된다.
     운동과 인바디를 기록하는 앱이다. 그게 전부다.

후 : 쉬웠던 날은 없었다. / 그래서 전부 값이 있다.
     빠진 날까지 전부 남는다. / 언젠가 처음부터 읽게 된다.
```

- 전 문구는 조건절(`~적으면`)로 열어서 **첫 줄이 혼자서는 아무 말도 안 했다.** 큰 글씨 한 줄이 미완성 문장이면 히어로가 아니다
- `기록하는 앱이다` 는 앱이 자기소개를 하는 문장이다. 화면을 여는 사람이 궁금한 건 앱이 뭐냐가 아니라 자기가 한 게 어떻게 되냐다
- 시안을 스무 개 넘게 돌렸다. 버려진 방향이 셋이다 — **장치 설명**(적으면 쌓인다)은 밋밋하고, **응원**(전부 네 것이 된다)은 느끼하고, **담백**(무게는 숫자로 남는다)은 아무 말도 안 한다
- 남은 것의 공통점은 **주어가 없다는 것**이다. `너` · `네 기록` 같은 말이 없다. 누구 얘기인지 안 밝히니까 읽는 사람이 자기 얘기로 읽는다
- 밑줄은 한 줄로 흘리지 않고 끊었다. 흘려 쓰면 설명이 되고, 끊으면 문장이 선다. 앞은 지금을 안심시키고(빠져도 남는다) 뒤는 나중을 걸어둔다(언젠가 읽게 된다)
- 강조는 `경험치`(장치 이름)에서 `값`(값어치)으로 옮겼다

**히어로만 바꾸면 아래가 어긋나서 같이 손봤다**

- `이번 주는 0일 했다` — 안 나온 주에 화면이 사람을 나무랐다. 0 일 때는 세는 대신 `이번 주는 오늘이 첫 날이 된다` 로 바꾼다. 1일 이상이면 `이번 주만 N일 나왔다`
- 기록이 없을 때 `아직 기록이 없다` → **`누구의 첫 줄도 대단하지 않았다 / 한 세트면 충분하다`**. 없는 것을 지적하지 않고, 비교당할 걱정을 먼저 내려놓게 한다. 뒷줄은 시키는 말이 아니라 허락에 가깝게 짧게 끊었다
- `지금까지 N회 기록했다` 는 한 번 `하나도 안 사라졌다` 로 바꿨다가 **다시 `지금까지 N회 적었다` 로 되돌렸다.** 히어로가 이미 `빠진 날까지 전부 남는다` 라고 말한다. 바로 아래에서 같은 말을 또 하면 수를 두 번 쓰는 것이다

**안 바꾼 것 — 한 화면에서 감정을 쓰는 자리는 하나여야 한다**

- `기록하러 가기 →` — 버튼은 누르면 뭐가 되는지만 말한다. 여기에 멋을 부리면 누를 때 망설인다
- 레벨 규칙 설명 — 감성을 넣으면 규칙이 안 읽힌다
- `운동을 계속할 이유를 하나 더 만들어 두는 장치다` — 앱이 자기 속셈을 밝히는 문장이다. 이 페이지에서 제일 정직한 줄이라 손대면 손해다
- 제보함 안내는 **존댓말 그대로** 둔다. 부탁하는 자리라 말투가 달라야 한다
- 섹션 라벨 · FAQ · 앱 정보 — 길잡이가 문학이면 길을 잃는다

- **고른 기준은 "이 자리에 놓였을 때"** 다. C·E 는 잘 만들수록 홈 탭과 하는 일이 겹친다. D 의 약점("훑기보다 읽어야 한다")은 매일 여는 화면일 때 값을 치르는데, 이 페이지는 `더보기` 안이라 그 값을 거의 안 낸다
- 숫자는 손으로 적지 않는다 — 레벨 상한 · 등급 이름 · 등급 수 · 티켓 규칙 · 교환비 · 앱 버전을 전부 실제 상수와 등급표, `package.json` 에서 읽는다. **일반 만렙 등급을 `신화` 로 적어뒀었는데 실제로는 `이름 없는 것` 이었다** — 손으로 적으면 이렇게 어긋난다

**제보함 — 유형을 고르면 그 다음이 달라진다**

셋을 같은 폼으로 받으면 버그는 정보가 모자라고 문의는 쓸데없이 길어진다.

- **버그** — 어느 화면인지 · 다시 해도 그런지(매번/가끔/한 번만)를 묻고 기기 정보를 기본으로 붙인다. 재현할 수 있어야 고친다
- **문의** — 제목만 있으면 된다. 내용 칸은 3줄로 줄고 기기 정보도 안 붙인다
- **건의** — `지금은 어떻게 하고 계신가요`(방법이 없다/불편하게 돌려서 한다/없어도 된다)를 묻는다. 대안이 있는지가 순서를 정한다
- **막는 것은 유형과 제목뿐이다.** 처음엔 화면·빈도·내용 10자까지 넷을 다 요구했는데, 제목을 쓰고도 버튼이 죽어 있다는 지적을 받았다. 못 보내게 막는 것보다 부실하게라도 받아서 되묻는 편이 낫다. 나머지는 `…까지 적어주시면 더 빨리 찾습니다` 로 회색 안내만 한다
- 지우기 두 곳 — 쓰던 것 비우기(뭔가 썼을 때만 나온다)와 보낸 제보 지우기. 카드 누르기가 접기/펼치기라 **지우기는 한 번 더 묻는다**
- 목록에 꼬리표가 붙는다 (버그는 `미니게임` `매번 그래요`, 건의는 `불편하게 돌려서 해요`)

**공지는 사람이 쓰지 않는다**

사람이 적으면 두 가지가 어긋난다 — 적는 걸 잊어서 목록이 비거나, 적어놓고 실제와 달라지거나.

- `scripts/gen-changelog.mjs` 가 **git 커밋에서 `feat`·`fix`·`perf` 만** 뽑아 `src/data/changelog.json` 을 만든다. `chore`·`docs`·`refactor` 와 `(dev)` 범위는 화면이 안 바뀌므로 뺀다
- `predev`·`prebuild` 로 **자동 실행**된다. 커밋하면 목록이 알아서 따라온다
- **커밋 본문(`%b`)이 화면에서 펼쳐 보는 세부 내용이 된다.** 이미 커밋마다 자세히 적고 있었으니 따로 쓸 것이 없다
- 커밋 제목으로 설명이 안 되는 것, 미리 알려야 하는 것은 `src/data/notices.json` 에 손으로 적는다. `pinned: true` 면 날짜와 상관없이 맨 위
- 둘은 `pages/preview/feed.jsx` 에서 한 목록으로 합쳐진다 — 공지는 오렌지, 커밋에서 온 것은 회색. 같은 날이면 공지가 먼저다 (커밋은 무슨 일이 있었는지를, 공지는 그게 무슨 뜻인지를 말한다)
- git 이 없거나 저장소가 아니어도 **스크립트는 실패로 끝나지 않는다.** 있던 json 을 두고 조용히 빠진다 — 빌드를 막을 이유가 없다
- **공지함**(`/preview/notices`)에 전부 있다. 종류로 거르고 날짜별로 묶는다. 홈페이지의 `최근 바뀐 것` 여섯 줄과 **같은 목록을 본다**

**남은 것** — 제보함 서버 연결(백엔드 `notices` 테이블 전환) · 탭 이름 결정 · 공지함 라벨(`제거` 가 `새 기능` 으로 뜬다) · 점검 예정 실제 렌더 확인 · FAQ 문답 검토. 붙이는 것은 8/24(월) 예정.

**원판 피하기 — 피하기 보상 폐지, 점수는 주워야만 오른다**
- 원판이 바닥에 닿을 때마다 자동으로 붙던 `+1`(`DODGE.dodgeReward`)을 없앴다. 이제 **바닥 원판을 밟아 주운 값만** 점수가 된다 — 가만히 피하고만 있으면 판이 끝날 때까지 0
- 없앤 이유: 가만히 피하는 게 가장 안전한데 벌이도 같이 따라와서, "낙하 구간으로 다시 들어가 줍는다"는 이 게임의 유일한 판단이 있으나 마나였다. 한 판에 원판 120개가 떨어지니 피하기만으로 티켓 12장이 들어왔다
- `dodged` 는 그대로 센다 — 낙하 속도·생성 간격이 여기에 걸려 있고 결과창의 `피함 N` 표시에도 쓴다. 난이도 곡선은 전과 동일
- 원판표의 `피하면 🥏 +1` 행은 `피하기만 하면 🥏 0` 으로 바꿔 규칙을 못 보고 지나칠 수 없게 했다
- 착지 처리에 있던 `setScore` 도 뺐다 — 점수가 안 변하는데 원판이 떨어질 때마다 리렌더를 한 번씩 일으키고 있었다
- 수급은 줄어든다. 확률·교환비(🥏 10 → 🎫 1)·하루 판 수는 손대지 않았으니, 조일 게 아니라 풀 거라면 잭팟 `weight` 나 `GROUND.lifeMs`(바닥에 남는 4.2초)를 보는 게 맞다

**교환 수량 버튼 — 꾹 누르면 계속 오른다** (`useHoldRepeat`)
- 교환소에서 100장을 담으려면 `+10` 을 열 번 눌러야 했다. "최대"는 지갑을 통째로 담는 것뿐이라 그 사이 값은 연타밖에 방법이 없었다
- 두 화면이 같은 훅을 쓴다 — **교환소**(`+1`·`+5`·`+10`)와 **미니게임 티켓 교환**(`−`·`+`)
- 380ms 누르면 반복이 시작되고, 간격이 170ms → 40ms 로 짧아진다(×0.85). 짧게 탭하면 전과 똑같이 1만 움직인다 — `pointerdown` 에서 한 번 실행하고, 키보드(Enter·Space)는 `click.detail === 0` 으로만 받아 두 번 세지 않는다
- 상한에 닿으면 그 자리에서 멈춘다. 동작이 `false` 를 돌려주면 반복이 끝나는 구조
- **손 떼는 것은 `window` 에서 받는다.** 반복 중에 버튼이 `disabled` 되면 그 요소로는 `pointerup` 이 오지 않아서, 버튼에만 걸어두면 손을 떼도 계속 올라간다. 앱을 나갔을 때(`visibilitychange`)와 창이 포커스를 잃을 때도 멈춘다
- 헤드리스 Chrome 으로 확인: `+` 꾹 1.5초 → 1→7, 손 떼면 7에서 정지, 계속 누르면 최대 50에서 정확히 멈춤, 짧게 탭은 +1. 교환소도 `+10` 꾹 1.8초 → 80장(🎫 16,000)

**교환소 `최대` — 잠금 해제 + 꾹 누르면 교환 반복**
- 담아둔 수량이 꽉 차면(`pending >= affordable`) `최대` 도 같이 회색으로 죽었다. 이제 **바꿀 일반 티켓이 하나라도 있으면 언제나 눌린다** (`maxOk = unlocked && affordable >= 1`). 이미 꽉 찬 상태에서 눌러도 같은 값을 다시 넣을 뿐이라(React 가 같은 값이면 리렌더도 안 한다) 잠글 이유가 없었다
- **꾹 누르고 있으면 담기 + 확정이 반복된다.** 지갑이 빌 때까지 울트라 티켓이 계속 늘어난다
- **짧게 탭하면 지금까지처럼 담기만 한다.** 한 방향 교환이라 되돌릴 방법이 없어서 확정 단계를 둔 것인데, 스친 손가락 한 번에 지갑이 비면 그 안전장치가 무의미해진다. 되돌릴 수 없는 일을 하려면 0.4초를 계속 누르고 있어야 한다
- 이걸 위해 `useHoldRepeat` 이 동작에 `isRepeat` 을 넘기게 했다 — 첫 누름은 `false`, 꾹 눌러 반복되는 동안은 `true`. 탭과 홀드가 서로 다른 일을 할 수 있다
- 반복 중 교환은 `확정` 버튼과 같은 `busyRef` 연타 방어를 공유한다. 다만 아직 반영 전이면 그 tick 만 거르고 넘어간다 — 여기서 멈춰버리면 손은 누르고 있는데 아무 일도 안 일어난 채로 끝난다
- 꾹 누르기는 화면에 안 보이는 동작이라 버튼 줄 아래에 `최대를 꾹 누르고 있으면 바로 교환됩니다` 를 적었다
- `+1`·`+5`·`+10` 은 그대로 상한에서 잠근다 — 눌린 뒤 실패하면 왜인지 알 수가 없어서다
- 확인(🎫 40,000): 짧게 탭 → 수량 200 담기고 지갑 그대로 · 꾹 1.5초 → 일반 0 / 울트라 200 으로 교환되고 바꿀 게 없어져 버튼이 잠김
