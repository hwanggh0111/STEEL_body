# 어디가 느린가 — 재본 값 (2026-09-18)

```
cd backend && npm run bench          사람 1명 · 5년치
cd backend && npm run bench -- 10    사람 10명을 같이 넣고
```

**짐작으로 고치지 않으려고 만든 자리다.** 이 앱에서 여태 잡은 느린 자리는 전부
재본 뒤에 드러났고, 재고 나면 고칠 자리가 대개 한 줄이었다.

검사가 아니다 — 통과·실패가 없다. 수를 적어두고 **다음에 견준다.**
기계마다 다르므로 아래 값은 「이 PC 에서 2026-09-18 에」 잰 것이다.

## 오늘 이 값을 보고 고친 것

**하루치 조회가 표 전체를 훑고 있었다** (`db.getWorkoutsByDate`) — 모든 사람의 모든 줄을
훑어 걸렀다. 내 목록은 이미 표에 들고 있으므로(5초) 거기서 걸러내면 **남의 줄은 아예 안 본다.**

```
3.28 ms  →  0.48 ms      (같은 자료, 사람 10명 · 29만 줄)
```

달력이 날마다 부르는 자리라 한 달이면 서른 번이다 — 100ms 가 15ms 가 된다.

## 다음에 손댈 자리 (순서대로)

1. **DB 이사** — 위 표의 첫 두 줄이 그대로 이유다. 저장 한 번이 **173 + 196 = 369ms** 고,
   줄이 늘수록 길어진다. 이 DB 는 **파일 한 장을 통째로 읽고 쓴다.**
   무거운 사용자(5년 · 하루 16줄) 스무 명쯤에서 힙 뚜껑(448MB)에 닿는다.
   → 「배포하자」 할 때 함께 정하는 일이다 (`docs/TODO-2026-09-18.md` 의 2번)
2. **사진을 통째로 안 들고 있기** — 사람마다 4MB 다. 지금은 `photos.json` 을 통째로
   캐시한다. DB 이사와 같은 자리에서 같이 정리하는 것이 맞다 (따로 손대면 두 번 고친다)
3. **내 운동 전부 10.5ms** — 표에 없을 때만이라 지금은 급하지 않다. 손대려면
   사람별 색인을 두는 일인데, 1번을 하면 저절로 없어지는 문제다

**위 셋은 전부 1번으로 모인다.** 그래서 지금 따로 고치지 않는다 —
고쳐두면 이사할 때 두 번 버린다.

## 재는 자리를 늘릴 때

`backend/scripts/bench.cjs` 에 한 줄 더하면 된다. 다만 두 가지는 지킨다 —

- **진짜 DB 를 안 건드린다** (`DB_FILE` 로 임시 파일을 쓰고 지운다)
- **글자를 돌려쓰지 않는다.** 사진을 잴 때 같은 글자를 서른 번 넣었더니 자바스크립트가
  하나만 들고 있어서 메모리가 1.4MB 밖에 안 늘었다 — 하마터면 「사진은 가볍다」로
  읽을 뻔했다. 사람마다 다른 자료라야 진짜 값이 나온다
