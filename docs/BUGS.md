## M1. 게임 중 원판표를 열 수 있다 — ✅ 수정됨

**파일** `frontend/src/components/PlateDodge.jsx:753` (원판표 버튼), `:510` (`canShop`)

**무엇이 잘못됐나**

교환창은 판이 도는 중에 못 열도록 막혀 있습니다.

```js
const canShop = affordable > 0 && phase !== 'playing' && phase !== 'revive';
```

**원판표 버튼에는 이 가드가 없습니다.** `onClick={() => setShowRates(true)}` 뿐이고 `disabled`도 없습니다. 게임 중에 눌리고, 모달이 화면 전체를 덮는 동안 rAF 루프는 계속 돕니다 (`phase`가 여전히 `'playing'`이므로). 게다가 `pointermove` 리스너가 `window`에 붙어 있어 **화면이 가려진 채로 캐릭터가 마우스를 따라 움직입니다.**

이건 이미 한 번 고친 버그와 같은 종류입니다 — 기존 보고서의 "게임 중 교환창 열림 → 게임이 뒤에서 계속 돌아 가려진 채 죽던 것". 교환창만 막고 원판표를 빠뜨렸습니다.

**재현** (실제로 확인함)

```
경로: /minigame
시작 클릭 → 2.5초 후 화면 점수 = 🥏 1
게임 중 원판표 버튼: clicked      ← 막혀 있지 않음
모달 떠 있음: true
모달 3초 후 화면 점수 = 🥏 10     ← 뒤에서 계속 돌았다
```

**어떻게 고쳤나** (2026-08-17)

두 버튼이 같은 조건을 쓰도록 `inRun`으로 묶고, 원판표 버튼에도 `disabled`를 걸었습니다.

```js
const inRun = phase === 'playing' || phase === 'revive';
const canShop = affordable > 0 && !inRun;
```

판을 시작할 때 열려 있던 창도 닫습니다(`setShowShop(false)` / `setShowRates(false)`) — 지금 구조에서는 모달이 시작 버튼을 덮어 일어날 수 없지만, 레이아웃이 바뀌면 바로 되살아날 종류의 버그입니다.

**재수정 후 재현 결과**

```
게임 시작 후 화면 점수 = 🥏 1
게임 중 원판표 버튼: disabled     ← 막힘
→ 원판표가 게임 중에 막혀 있습니다
```

## M2. 게임 중 새로고침하면 그 판이 통째로 날아간다 — ✅ 수정됨

**파일** `frontend/src/components/PlateDodge.jsx:101` (언마운트 정산), `:297` (`startRun`)

**무엇이 잘못됐나**

판 수는 시작할 때 깎습니다(`startRun()`). 이건 맞습니다 — 끝날 때 깎으면 지기 직전에 새로고침해서 무한히 돌 수 있으니까요.

그래서 "화면을 벗어나면 그때까지 번 원판을 넣어준다"는 정산이 붙어 있는데, **그게 React 언마운트에만 걸려 있습니다.**

```js
useEffect(() => () => {
  const p = phaseRef.current;
  if ((p === 'playing' || p === 'revive') && gameRef.current) {
    finishRun(gameRef.current.raw);
  }
}, [finishRun]);
```

새로고침·탭 닫기·브라우저 종료에는 cleanup이 돌지 않습니다. **판 수는 깎였는데 번 원판은 0이 됩니다.**

**재현** (실제로 확인함)

```
시작 전     plates=null   day=null
게임 중     day="2026-08-17|1"   화면 점수 🥏 1
새로고침 후 plates=null   day="2026-08-17|1"

판 수 소모 = 1,  얻은 원판 = 0
```

**이득을 보는 방법은 아닙니다** — 새로고침하면 손해만 봅니다. 그래서 악용은 안 되지만, 실수로 F5를 누르면 하루 5판 중 한 판이 그냥 없어집니다.

**어떻게 고쳤나** (2026-08-17)

정산 로직을 `settleRun()`으로 빼고 **`pagehide`에도 붙였습니다.** `beforeunload`가 아니라 `pagehide`인 이유는 모바일 사파리에서도 뜨고 bfcache 진입에도 뜨기 때문입니다.

정산 경로가 셋(죽음 / 라우팅 이탈 / 페이지 종료)이 되었으므로 `settledRef` 플래그로 중복을 막습니다. `endRun`도 이 플래그를 세웁니다 — `setPhase('over')`는 다음 렌더에나 반영되므로, 그 사이에 `pagehide`가 뜨면 `phaseRef`가 아직 `'playing'`이라 두 번 들어옵니다.

**재수정 후 재현 결과**

```
시작 전     plates=null   day=null
게임 중     day="2026-08-17|1"   화면 점수 🥏 4
새로고침 후 plates="4"    day="2026-08-17|1"

판 수 소모 = 1,  얻은 원판 = 4  ✅
```

## M3. 회원가입으로 계정을 갈아타면 앞 계정의 지갑이 넘어온다 — ✅ 수정됨

**파일** `frontend/src/store/authStore.js:47` (`register`), `:39` (`login`의 가드), `frontend/src/App.jsx:53` (`/register` 라우트)

**무엇이 잘못됐나**

파칭코 EXP와 원판 지갑은 localStorage에 **계정 구분 없이** 저장됩니다. 그래서 로그인에는 계정이 바뀌면 비우는 가드가 있습니다.

```js
if (prevEmail && data.email && prevEmail !== data.email) {
  usePachinkoStore.getState().reset();
  usePlateStore.getState().reset();
}
```

**`register`에는 이 가드가 없습니다.** 그리고 `/register`는 `PrivateRoute` 밖이라 **로그인한 상태로도 들어갈 수 있습니다.**

→ A로 로그인해 원판·티켓·EXP를 쌓아둔 채 `/register`에서 B를 만들면, A의 지갑과 레벨이 그대로 B의 것이 됩니다. 백엔드 응답에 `email`이 들어 있으므로(`auth.js:210`) 비교할 재료는 이미 있습니다.

**곁가지** — `login`의 가드는 `prevEmail`이 있어야 돕니다. 정상 흐름에서는 로그아웃이 `ironlog_email`과 두 스토어를 함께 비우므로 문제가 없지만, `ironlog_email`이 없던 시절의 데이터가 남아 있는 브라우저에서는 첫 로그인 때 앞 사람 진행도를 물려받습니다.

**어떻게 고쳤나** (2026-08-17)

`register`에도 리셋을 넣었습니다. 가입은 언제나 새 계정이고 물려받을 진행도가 없으므로 **조건 없이** 비웁니다 (`login`처럼 이메일을 비교할 필요가 없습니다).

```js
usePachinkoStore.getState().reset();
usePlateStore.getState().reset();
```

가입 요청이 실패하면(중복 이메일 등) `await`에서 throw하므로 리셋은 실행되지 않습니다.

**검증 수준** — 이 항목만 **코드 확인에 그쳤습니다.** 실제로 확인하려면 계정을 하나 만들어야 해서 DB에 테스트 계정을 남기게 되므로 돌리지 않았습니다. M1·M2는 브라우저로 재현·통과까지 확인했습니다.

**남겨둔 것** — 로그인한 상태로 `/register`에 들어가는 것 자체는 여전히 됩니다(`PrivateRoute` 밖). 지갑이 안 넘어가므로 피해는 없지만, 막고 싶으면 라우트 가드를 추가하면 됩니다.

## P0-1. 연출 도중 이탈하면 티켓이 환불된다 (사다리 3.6초 창) — ✅ 수정됨

**파일** `frontend/src/components/LadderGame.jsx:117` (언마운트 `release`), `:169` (`play` 호출)

**무엇이 잘못됐나**

티켓 회계가 2단계입니다.

1. 판을 시작할 때 `reserve(n)` — `pending`만 올라감 (localStorage 미기록)
2. 연출이 끝날 때 `play()` — 그제서야 `used`가 올라가고 localStorage에 기록

그 사이에 컴포넌트가 언마운트되면 cleanup이 `release(inFlightRef.current)`를 불러 **예약을 되돌립니다.** `used`는 끝내 오르지 않습니다. 새로고침해도 같습니다 — `pending`은 저장하지 않으므로 사라지고, `used`는 애초에 안 올랐습니다.

**왜 치명적인가**

사다리는 **시작 즉시 5칸의 보상이 전부 화면에 표시되고, 가로줄도 전부 보입니다.** 즉 눈으로 경로를 따라가면 3.6초 연출이 끝나기 훨씬 전에 결과를 알 수 있습니다. 꽝이면 탭을 벗어나거나 새로고침 → **티켓 100장 전액 환불.**

기대값을 무한대로 만드는 구조적 결함입니다. 꽝만 골라서 무를 수 있으면 사다리는 손해 볼 수 없는 게임이 됩니다.

**재현**

1. `/pachinko` 이동, 티켓 100장 이상 확보
2. 사다리 시작점 클릭
3. 선이 도착 칸에 닿기 전에 보상 위치를 눈으로 확인
4. 꽝이면 즉시 새로고침
5. 보유 티켓이 줄지 않았는지 확인

**파칭코도 같은 구조지만 창이 훨씬 좁습니다** — 마지막 릴이 2008ms에 멈추고 `play()`는 2200ms에 커밋되므로 **약 190ms**. 실현 가능성은 낮지만 원인은 동일합니다.

**어떻게 고쳤나** (2026-08-17)

`used`를 **판 시작 시점에 확정**하고, 연출은 이미 정해진 결과를 보여주기만 하게 바꿨습니다. 원판 피하기의 `plateStore.startRun()`과 같은 방식입니다.

스토어 API가 두 단계로 갈렸습니다.

- `beginPlay(cost)` — 판을 시작하는 즉시 `used` 증가 + localStorage 기록
- `award(prize, mode)` / `awardMany(rows, mode)` — 연출이 끝나면 보상만 반영

`reserve` / `release` / `pending`은 필요 없어져 전부 걷어냈습니다 (`PachinkoPage`, `MiniGamePage`, `dev/setLevel.js`의 참조 포함).

**대신 생기는 문제도 같이 막았습니다.** 티켓이 먼저 나가므로 연출 도중 이탈하면 티켓만 날리게 됩니다. 그래서 뽑은 보상을 `inFlightRef`에 들고 있다가 **언마운트 때 정산**합니다 — 티켓이 나갔으면 보상은 반드시 지급됩니다. 새로고침은 원래 `used`가 이미 기록돼 있으므로 티켓만 정상 소모되고, 그 판의 보상은 받지 못합니다(결과를 못 본 채 나간 것이므로 의도된 동작).

## P0-2. 구매 티켓이 localStorage에 있어 조작 가능 — ✅ 방침 확정 (b)

**파일** `frontend/src/data/plateData.js:112` (`PLS.purchased`), `frontend/src/components/PachinkoSystem.jsx:76` (`earnedTickets`)

**무엇이 잘못됐나**

원래 티켓 설계는 이렇습니다 (`pachinkoData.js:4` 주석):

> 티켓은 "발급량 = 기록 수에서 계산" + "사용량만 localStorage 누적" 구조.
> **발급량을 저장하지 않으므로 티켓 자체를 조작할 수 없습니다.**

원판 피하기로 산 티켓(`purchased`)을 발급량에 더하면서 이 보장이 깨졌습니다. `purchased`는 저장되는 값이라 콘솔 한 줄로 무제한 발급됩니다.

```js
localStorage.setItem('steelbody_plate_tickets', '999999')
```

하루 판 수 제한(`dailyPlays`)으로 벌이를 묶어놨지만, 그건 정직하게 플레이할 때만 유효합니다.

**참고** `used`도 localStorage라 `0`으로 되돌리면 티켓이 재충전됩니다. 이건 원래부터 있던 구멍이지만, 같은 층위의 문제라 같이 판단해야 합니다.

**선택지**

- (a) 서버에 티켓 원장을 두고 검증 — 정석이지만 백엔드 작업 필요
- (b) 조작 가능성을 받아들이고 문서화 — 혼자 쓰는 앱이면 합리적
- (c) 서명/체크섬으로 캐주얼한 조작만 차단 — 비용 대비 효과는 낮음

**결정: (b)** (2026-08-17)

레벨은 남과 겨루는 값이 아니라 자기 기록을 보는 지표라, 서버 원장을 둘 만큼의 값어치가 없다고 판단했습니다. 조작하고 싶은 사람은 자기 숫자만 망칠 뿐입니다.

**대신 코드가 거짓말하지 않게 맞췄습니다.** 원래 `pachinkoData.js` 상단에 "발급량을 저장하지 않으므로 티켓 자체를 조작할 수 없습니다"라고 적혀 있었는데, `purchased`가 생기면서 사실이 아니게 된 채 남아 있었습니다. 이제 어떤 키가 열려 있는지까지 적어 뒀습니다.

```
steelbody_plate_tickets   원판 피하기로 산 티켓
steelbody_pachinko_used   사용량 (0으로 되돌리면 티켓이 재충전됨)
steelbody_pachinko_exp    누적 EXP
```

`PachinkoSystem.jsx`의 `earnedTickets` 주석에 있던 "(조작 불가)"도 같이 지웠습니다.

**이 결정이 뒤집히는 조건** — 랭킹처럼 **남과 비교하는 요소**가 들어오는 순간 (b)는 성립하지 않습니다. 그때는 (a)가 필요합니다.

## P1-1. 상한 초과 티켓 소멸이 유저 자산을 태운다 — ✅ 수정됨

**파일** `frontend/src/pages/PachinkoPage.jsx:38` (`trimOverflow` effect), `frontend/src/store/pachinkoStore.js:38`

**무엇이 잘못됐나**

`available = min(earned - used, maxStack)`이 표시만 상한에 묶어서, `earned - used > maxStack`인 계정은 티켓을 써도 숫자가 줄지 않는 **무한 티켓 버그**가 있었습니다. 이건 `trimOverflow`로 고쳤습니다 (넘친 만큼 `used`로 밀어 실제 소멸).

**남은 문제:** 이제 상한 초과분이 **진짜로 사라집니다.** 운영 `maxStack`은 150이고 `earned`는 운동 3회당 1장이므로, **운동 450회를 기록한 유저가 파칭코 페이지를 열기만 해도** 그때까지 안 쓴 티켓이 150장으로 잘립니다. 예고도 없고 되돌릴 수도 없습니다.

의도된 설계(무한 적립 방지)를 실제로 작동시킨 것이라 "버그"라 부르긴 애매하지만, **유저가 체감하는 손실**이라 그대로 두면 민원이 됩니다.

**선택지**

- 소멸 전에 안내 (모달 또는 토스트 1회)
- 또는 상한을 크게 올려 실질적으로 안 걸리게
- 또는 상한을 없애고 `available = earned - used`로 단순화

**결정: 상한은 유지하고 안내를 붙인다** (2026-08-17)

무한 적립 방지라는 원래 의도는 살리되, 말없이 자산이 타는 것만 막았습니다. 두 군데에서 알립니다.

| 시점 | 어디 | 내용 |
|---|---|---|
| **소멸 전** | 파칭코 헤더 티켓 숫자 아래 | `상한 · 더 안 쌓여요` (상한에 닿아 있는 동안 계속) |
| 소멸 직후 | 토스트 (warning) | `보유 상한 150장을 넘은 티켓 N장이 사라졌어요` |

`trimOverflow`는 원래부터 소멸량을 반환하고 있었는데 호출부가 버리고 있었습니다. 그 값을 그대로 씁니다.

미니게임 쪽은 이미 막혀 있습니다 — `PlateDodge`가 `ticketRoom`으로 상한 초과 구매를 차단하고 `ticketFull` 상태를 표시합니다.

## P1-2. 다회 뽑기 합계가 2^53을 넘으면 표시가 부정확 — ✅ 수정됨

**파일** `frontend/src/store/pachinkoStore.js:85` (`sum`), `frontend/src/components/PachinkoSystem.jsx` 요약 패널

**무엇이 잘못됐나**

```js
const sum = rows.reduce((s, r) => s + r.prize.exp * r.count, 0);
const nextGained = Math.min(gained + sum, MAX_EXP);
```

`nextGained`는 `MAX_EXP`(8,999,999,999,999,999 — 2^53 안쪽)로 잘리므로 **저장값은 안전합니다.**

문제는 `sum` 자체와, 반환되는 `rawTotal`, 그리고 요약 패널의 등급별 `p.exp * count`입니다. 초신성 1회가 999,999,999,999,999이므로 **10회만 나와도 1e16으로 2^53을 넘어** 정밀도가 깨집니다. 티켓 999만 장을 "모두 쓰기" 하면 초신성이 10회 안팎 나오므로 실제로 도달합니다.

증상: 요약 패널의 숫자가 미세하게 틀리거나 끝자리가 0으로 뭉갭니다. **저장·레벨 계산은 멀쩡합니다.**

**어떻게 고쳤나** (2026-08-17)

`awardMany`가 `exp * count`를 누적하면서 매번 `Number.isSafeInteger`로 확인하고, 안전 범위를 벗어나는 순간 합산을 멈춰 `exact: false`로 표시합니다. 그 경우 합계는 `MAX_EXP`로 확정합니다.

화면에서는 `exact: false`일 때 **틀린 수를 보여주지 않습니다.**

- 요약 패널 총합 → `상한 도달` / `MAXED`
- 등급별 줄 → 횟수만 남기고 `+EXP` 숨김
- 토스트 → `N회 — 상한 도달`

저장·레벨 계산은 원래부터 `MAX_EXP`에서 잘려 정상이었고, 지금도 그대로입니다.

## 진짜 무한 티켓 (`unlimited`)

울트라 무한을 주우면 **파칭코와 사다리에서 티켓이 영구히 닳지 않습니다.**

### "티켓 N장 지급"이 아니라 "소모를 멈춘다"

이게 구현의 전부입니다.

```js
// pachinkoStore.beginPlay
if (usePlateStore.getState().unlimited) return true;   // used 를 올리지 않는다
```

다른 방법들이 왜 안 되는지:

| 방법 | 문제 |
|---|---|
| 지갑에 `Infinity` 저장 | `String(Infinity)` → `readInt`의 `isFinite` 가드에 걸려 다음 접속에 지갑이 0 |
| 지갑에 큰 수 저장 | 결국 유한하고, 보유 상한(`maxStack` 150)에도 걸림 |
| **소모를 멈춤** | **숫자를 아예 안 건드리므로 깨질 게 없음** ← 채택 |

`available`은 화면과 "모두 쓰기"가 쓸 수 있게 유한한 큰 수(`UNLIMITED_TICKETS = 9,999,999`)를 쓰고, **표시만 `∞`**로 바꿉니다. 이 규모는 개발 보너스로 이미 쓰던 값이라 다회 뽑기 경로가 검증돼 있습니다.

세 화면이 같은 식을 쓰도록 `ticketsAvailable({ earned, used, unlimited })` 하나로 모았습니다.

### 함께 꺼지는 것들

| | 이유 |
|---|---|
| `trimOverflow` (상한 소멸) | 상한 자체가 의미 없음 |
| `atCap` 경고 (`상한 · 더 안 쌓여요`) | 위와 같음 |
| 미니게임 티켓 교환 | 살 이유가 없음. `ticketRoom = 0`이 되고 버튼에 `∞ 무한 티켓 보유 중` |

계정 전환 시에는 `plateStore.reset()`이 플래그(`steelbody_plate_unlimited`)도 함께 지웁니다.

### 획득 시점

**바닥에서 줍는 즉시** 확정합니다(판이 끝날 때가 아니라). 판 정산을 못 하고 나가면 9년에 한 번을 날리기 때문입니다.

### 색

이 등급만 단색이 아니라 **무지개가 회전합니다** (`createConicGradient`, 떨어질 때도 바닥에서도). 단색으로는 "그냥 좋은 원판"과 구분되지 않아서입니다. `createConicGradient`가 없는 브라우저에서는 조용히 단색으로 떨어집니다.

### 검증 (2026-08-17)

헤드리스 Chrome에서 개발 가중치로 실제로 주워봤습니다.

```
무한 티켓 획득: 성공 ✅
획득 토스트: 떴음
새로고침 후 플래그: 1
파칭코 티켓 표시: 🎫 ∞
뽑기 전 used = null
100회 뽑은 뒤 used = null   (누적 EXP = 4710)
✅ 티켓이 ∞ 로 표시되고, 100회를 돌려도 used 가 오르지 않았습니다 (EXP 는 정상 지급)
```

### 경고

**한 번 뜨면 그 계정의 티켓 경제가 영구히 끝납니다.** 되돌리는 UI는 없습니다(localStorage에서 `steelbody_plate_unlimited`를 지우면 풀립니다). 9년에 한 번이라는 확률은 그래서입니다.

### 기대값 표기를 나눈 이유

울트라 무한 하나가 **산술 기대값의 65%**를 차지합니다. 9년에 한 번 뜨는 값을 "주울 때 평균"이라고 띄우면 매 판 그만큼 받는 것처럼 읽힙니다.

| | 값 |
|---|---|
| 주울 때 평균 (∞ 제외) | **2.74** ← 원판표 기본 표시 |
| ∞ 포함 | 7.73 (참고로만 같이 표시) |

`plateData.js`가 `EXPECTED_PER_PLATE`(전체)와 `EXPECTED_PER_PLATE_COMMON`(`legend: true` 제외) 둘을 냅니다.

### 왜 `Infinity`가 아니라 9,999,990인가

`value: Infinity`로 두면 **지갑이 다음 접속에 0이 됩니다.**

```
저장 String(Infinity) → "Infinity"
읽기 readInt → Number.isFinite(Infinity) === false → fallback 0
```

`readInt`의 손상값 방어 가드에 `Infinity`가 그대로 걸립니다. `best`(최고 기록)도 같이 날아갑니다. 그래서 **값은 크게 잡되 유한한 수로 두고, 보여줄 때만 `∞`로 바꿉니다** (`plateValueText`의 `display` 필드).

지갑·점수·상점 계산은 전부 진짜 숫자로 돕니다. ∞는 원판 자체의 값을 보여주는 자리(원판표, 결과 화면 칩)에만 나옵니다 — 지갑을 ∞로 찍으면 교환 계산이 거짓말이 됩니다.

### 잭팟 취급

둘 다 `value`가 `JACKPOT_VALUE`(100) 이상이라 잭팟 처리를 그대로 물려받습니다. 바닥 정리에서 보호되고(`ground`가 넘칠 때 값이 가장 낮은 것부터 지움), 9초를 버티며(`jackpotLifeMs`), 멀리서도 보이게 크게 빛납니다.

### 즉사 (`lethal: true`)

**울트라 무한에 맞으면 부활 횟수가 남아 있어도 그 자리에서 판이 끝납니다.** 이 게임에서 유일하게 목숨을 무시하는 원판입니다.

```js
// 게임 루프
if (!hitLethal && g.revives > 0) { setPhase('revive'); return; }
endRun(g, hitLethal);
```

최고 보상이자 최대 위험이라, 뜨는 순간의 판단이 "먹을까 피할까"가 아니라 **"일단 피하고 나서 주우러 갈까"**가 됩니다. 바닥에 떨어진 뒤에는 안전하게 주울 수 있으므로, 유일한 획득 경로가 "제대로 피한 다음 되돌아가기"입니다.

**세 군데에 알립니다** — 안 그러면 부활 버튼이 안 뜬 게 버그로 보입니다.

| 시점 | 어디 | |
|---|---|---|
| 뜨기 전 | 원판표 | 이름 옆에 빨간 `☠️ 즉사` 태그 |
| 떨어지는 중 | 게임 화면 | 붉은 테가 깜빡이고 발광이 2배 (`shadowBlur` 26 vs 12) |
| 맞은 뒤 | 결과 화면 | `☠️ 울트라 무한에 맞았습니다 — 부활 없이 그대로 끝납니다` |

흰색 몸통만으로는 "제일 좋은 것"으로만 보여서 달려들다 판이 끝납니다. 그래서 붉은 테를 따로 둘렀습니다.

### 울트라 무한만 규칙을 하나 깹니다

원판표에 "무거울수록 크고 빠르다"고 써 있지만 **울트라 무한은 제일 크되 느립니다** (`r 0.130`, `speed 1.15` — 슈퍼울트라의 1.45보다 느림).

즉사 판정이라 맞으면 판이 끝나고 화면의 원판도 함께 사라집니다. 1년에 한 번 뜨는 걸 손도 못 대고 날리면 보상이 아니라 벌입니다. 커서 눈에 확 띄되, 피했다가 주우러 돌아갈 시간은 주도록 했습니다.

### 검증 (2026-08-17)

헤드리스 Chrome으로 개발 가중치(즉사 원판 약 7%)에서 가만히 서서 반복해 죽여 봤습니다.

```
원판표:  울트라 무한  ☠️ 즉사  ·  6.9% · 주우면 +∞     ← 태그 붙음
판 4: ☠️ 즉사 — 부활 화면 없이 바로 결과 화면
  안내 문구: ☠️ 울트라 무한에 맞았습니다 — 부활 없이 그대로 끝납니다
돌린 판 4 · 일반 피격(부활 화면) 3회 · 즉사 1회
```

일반 원판에 맞으면 부활 화면이 뜨고, 울트라 무한에 맞으면 부활을 건너뛰고 결과 화면으로 갑니다.

### 같이 손본 것

확률 표기가 `toFixed(1)`이라 0.00199%와 0.000498%가 **둘 다 "0.0%"로 보였습니다.** 1% 아래는 유효숫자 3자리로 찍게 바꿨습니다(`fmtPct`). 막대 그래프에는 최소 폭을 줬고, 큰 수에는 천 단위 구분을 넣었습니다.

```
슈퍼울트라   0.0999%
무한        0.000999%
울트라 무한  0.00004995%
```

### 조정하려면

`plateData.js`의 `weight` 한 줄입니다.

| 울트라 무한 `weight` | 주기 (하루 5판) | ∞ 포함 평균 |
|---|---|---|
| 0.0005 | 약 334일 | 52.69 |
| 0.0001 | 약 4.6년 | 12.73 |
| **0.00005** | **약 9.1년** | **7.73** ← 지금 |
| 0.00001 | 약 45.7년 | 3.74 |

(∞ 제외 평균은 어느 쪽이든 **2.74**로 그대로입니다 — 이 등급만 빠지는 값이라 그렇습니다.)

값이 999만이라 `weight`를 10배 올리면 ∞ 포함 기대값이 6배 뜁니다. **희소성이 곧 밸런스입니다.**

다만 이제 실제 보상은 `value`가 아니라 **티켓 무한**입니다. 한 번 뜨면 그 계정의 티켓 경제가 영구히 끝나므로, 조일 곳은 `value`가 아니라 `weight`입니다.

## 슈퍼울트라 확률 조정 (2026-08-17)

원판표 전체를 기대값 기여도로 뜯어봤습니다. 답이 하나로 나왔습니다.

```
원판 하나를 주웠을 때의 기대값 기여도 (∞ 제외, 합계 634.0)
  2.5kg          34.0    5.4%   ###
  5kg            26.0    4.1%   ##
  10kg           40.0    6.3%   ###
  15kg           39.0    6.2%   ###
  20kg           35.0    5.5%   ###
  슈퍼울트라      450.0   71.0%   ###################################
  무한            10.0    1.6%   #
```

**슈퍼울트라 하나가 71%였습니다.** 나머지는 전부 합쳐도 29%입니다.

### 왜 문제인가

| | 값 |
|---|---|
| 한 판에 뜰 확률 (원판 120개 기준) | **45%** → 2.2판에 한 번 |
| 하루 5판을 다 주웠을 때 | **티켓 203장/일** |
| 운동으로 보유 상한(150장)을 채우려면 | **운동 450회** |

미니게임 **하루**가 운동 450회를 넘깁니다. 이러면 "운동 기록 → 티켓 → 파칭코 → 레벨"이라는 앱의 축에서 첫 칸이 무의미해집니다.

### 조정 결과

`weight: 0.5 → 0.1` (개발은 5로 게이팅 — 원래 DEV 미적용이라 테스트가 어려웠습니다)

| | 전 | 후 |
|---|---|---|
| 등장 확률 | 0.498% | **0.0999%** |
| 한 판에 뜰 확률 | 45.0% (2.2판) | **11.3% (8.8판)** |
| 하루 수급 | 203장/일 | **51장/일** |
| 주울 때 평균 (∞ 제외) | 6.31 | **2.74** |
| ∞ 포함 | 16.26 | 12.73 |

하루 51장이면 운동 153회분입니다. **거들어주되 대체하지는 않는 수준**입니다.

기본 등급(2.5~20kg)은 건드리지 않았습니다 — 다 합쳐야 기여도 27%이고, 값이 1~5라 어떻게 만져도 수급을 흔들지 못합니다. 여기서 더 조이려면 확률이 아니라 `DODGE.dodgeReward`(피하기만 해도 주는 +1)나 `PLATE_RULE.dailyPlays`를 봐야 합니다.
